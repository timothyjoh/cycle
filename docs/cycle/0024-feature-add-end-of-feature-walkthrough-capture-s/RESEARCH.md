# Research: Cycle 0024

## Cycle Context
SPEC.md (`docs/cycle/0024-feature-add-end-of-feature-walkthrough-capture-s/SPEC.md`) asks for a new `walkthrough_capture` step appended as the **last** step of the `feature` workflow in `src/defaults/workflows.yml` (after `documentation`), propagated to `.cycle/` via `npm run sync-defaults`. The step orchestrates an **optional, project-provided walkthrough hook** (convention: `.cycle/walkthrough.sh` present+executable, or an `engine.walkthrough_hook` configured command). When a hook is present, the engine invokes it via array-arg `spawn`/`spawnSync` (inheriting the curated child env, re-injecting `CYCLE_*` vars), collects the media it emits into the cycle artifact dir, and records a `walkthrough_artifacts`-style pointer on the cycle completion record (mirroring the failed-bash `stdout_artifact` pattern). When **no** hook is configured (cycle's own CLI repo), the step must skip cleanly as a silent success — no artifact, no `step.end{status:"failed"}`, cycle stays green. Hook non-zero exit routes through normal step-failure handling; a successful hook whose media/pointer write fails degrades with a `step.walkthrough_capture_failed`-style diagnostic event, omits the pointer, and never masks the cycle outcome or crashes. Scope excludes any built-in Playwright/headless capture and any workflow other than `feature`.

### Existing Patterns to Follow
- **`skip_unless` guard (file-presence skip)** — `src/engine/run-cycle.ts:314-334`. Runs for **any** step (bash or agent) before exec. Stats `join(artifactDir, step.skip_unless)`; if absent/unreadable it emits `step.end {status:"skipped", reason:"skip_unless_artifact_missing", artifact, duration_ms}` and `continue`s — a clean non-failing skip. This is the canonical "inert step" path, but it keys on a **file in the artifact dir**, not on hook presence; hook-presence discovery is new logic the planner must add.
- **Failed-bash stdout capture + pointer (the model the SPEC names)** — `src/engine/run-cycle.ts:579-609`. On a failed bash step: writes full `=== stdout ===\n…\n=== stderr ===\n…\n` to `join(artifactDir, "<step>.out")`, sets `stdoutArtifact = outPath`, and adds `stdout_artifact: <path>` plus a head-capped `stdout` excerpt (`MAX_STEP_END_STDOUT = 2000`, `src/engine/run-cycle.ts:183`) to the `step.end` event. The pointer field on `step.end` is the existing "surface produced media from the completion record" convention to mirror.
- **Best-effort write degrade with diagnostic event (the model the SPEC names)** — `src/engine/run-cycle.ts:584-594`. The `.out` write is wrapped in try/catch; on failure it emits `step.output_capture_failed { cycle_id, step, artifact, error }`, omits the pointer (`stdoutArtifact` stays `undefined`), and never mutates `r.exitCode`/`r.status` — the original failure routing is preserved. The new `step.walkthrough_capture_failed` event should follow this exact shape and best-effort discipline.
- **Other best-effort side-effects that never fail the cycle** — `appendDocumentationPaths` wrapped in try/catch (`src/engine/run-cycle.ts:562-566`), `accumulateTouchedFiles` wrapped in try/catch (`src/engine/run-cycle.ts:567-571`). Both swallow errors with `/* best-effort; never fail the cycle */`.
- **Defensive config read at the read site** — `cfg.engine.compress_output === true` (`src/engine/run-cycle.ts:384`) and the rate-limit cap coercion (`src/engine/run-cycle.ts:410-412`). Convention: absent/malformed config resolves to a safe default at the point of use. A `walkthrough_hook` read should follow this.
- **Subprocess discipline** — `spawn`/`spawnSync` with array args, `shell:false` everywhere: `execBashStep` (`src/engine/exec-bash.ts:11`), the porcelain snapshots (`src/engine/run-cycle.ts:105-109, 136-140, 365, 543-547`). Never `exec`/`execSync`/`shell:true`.
- **Artifact write naming for agent steps** — `src/engine/run-cycle.ts:491` writes `join(artifactDir, "<STEP>.upper().md")`. `STEP_ARTIFACTS` / `ARTIFACT_STEPS` (`src/engine/run-cycle.ts:44-58`) is the declarative artifact + completion-proof table; a bash-orchestration `walkthrough_capture` step is **not** an `.md`-artifact step and would not be added here unless it produces a proof-checked markdown artifact.
- **Failure handling / terminal routing** — `src/engine/run-cycle.ts:610-621`. On `r.status === "failed"`: `reflection` and `documentation` are non-fatal (`continue` after a `*.skipped` event); every other failed step emits `cycle.end {status:"failed", failing_step}` and returns `{status:"failed", failingStep}`. A failed walkthrough hook (non-fatal vs fatal) routing decision lives here. Bash-step success/failure is purely driven by exit code (`src/engine/exec-bash.ts:20-27`); there are no retries/timeouts inside `execBashStep` itself (the per-step wall-clock timeout `step_timeout_ms` is forwarded only to agent `runStep`, `src/engine/run-cycle.ts:426`, not to bash steps).
- **Observability / logging convention** — structured JSONL via `createLogger` (`src/engine/run-cycle.ts:248`, `src/engine/log.ts`). Every event is `await log.emit("<event.name>", { cycle_id, … })`. Events in the change area: `step.start`, `step.end`, `step.skipped`, `step.warning`, `step.timeout`, `step.completion_check`, `step.output_capture_failed`, `cycle.end`. New events should use `step.`-namespaced names with `cycle_id` first, matching `step.output_capture_failed`'s `{ cycle_id, step, artifact, error }` shape.
- **Idempotency / retry-safety** — Engine single-instance lock (`src/engine/engine-lock.ts`). Bash steps are excluded from the retry-skip gate (`step.agent !== "bash"` at `src/engine/run-cycle.ts:301`) and from the completion-proof / artifact machinery, so a bash-style walkthrough step re-runs on every attempt; its output path is deterministic (`join(artifactDir, …)`), so re-runs are last-write-wins. The `.out` capture is documented as idempotent/never gating control flow (`docs/ENGINE.md:199`).

## Open Questions
- **Dispatch mechanism**: SPEC describes engine-orchestrated `spawn`/`spawnSync` of the hook (`src/engine/run-cycle.ts` new code), but a `walkthrough_capture` step could also be a plain `agent: bash, command: …` step routed through `execBashStep`. Which dispatch path the planner chooses determines whether `skip_unless` (file-keyed) suffices for the inert-when-absent guard or whether new hook-presence detection (`.cycle/walkthrough.sh` executable check **or** `engine.walkthrough_hook` config) must be implemented in the loop. The existing `skip_unless` keys only on an artifact-dir file, not on a repo-root executable.
- **Completion-record target**: the existing `stdout_artifact` pointer lives on `step.end`; SPEC says "cycle completion record." Planner must decide whether `walkthrough_artifacts` attaches to the walkthrough step's `step.end`, to `cycle.end` (`src/engine/run-cycle.ts:624` currently carries only `cycle_id`/`status`), or both.
- **Artifact-dir env exposure**: a project hook needs the cycle artifact dir path; `cycleEnv` (`src/engine/run-cycle.ts:278-284`) does not currently export it. Planner must decide the env var name (e.g. `CYCLE_ARTIFACT_DIR`) and that it is re-injected via `extra` per the `buildChildEnv` contract.
- **Hook non-zero exit policy**: SPEC says non-zero exit routes through "normal step-failure routing" (fatal `cycle.end`), but the step is the workflow's last; planner should confirm whether a failed walkthrough should be fatal (like `verify`) or non-fatal/continue (like `documentation` at `src/engine/run-cycle.ts:615-617`).
- **Media collection semantics**: "collect media into the artifact dir" — whether the hook writes directly into `artifactDir` (engine only references existing files) or emits elsewhere and the engine copies. This affects what the write/collect-failure (`step.walkthrough_capture_failed`) path actually guards.
