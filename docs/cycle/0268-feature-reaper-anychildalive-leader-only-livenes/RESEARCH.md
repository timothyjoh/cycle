# Research: Cycle 0268

## Cycle Context
SPEC.md asks for a single, surgical change to the active-child reaper's liveness probe. Today `anyChildAlive` in `src/engine/active-child.ts` probes only the **group leader** (`process.kill(pid, 0)`), while `killActiveChildren` group-kills the **whole process group** (`process.kill(-pid, sig)`). The probe and the kill therefore disagree on what "the child" is: if a registered leader exits but a tool forked into its process group survives and ignores SIGTERM, `anyChildAlive` reads the dead leader, returns `false`, `reapAndExit`'s fast-poll exits the worker, and the SIGKILL backstop never fires — orphaning a still-mutating grandchild. The cycle makes the probe symmetric with the kill (`process.kill(-pid, 0)`), with `ESRCH` ⇒ this group is gone (does not count as alive) and `EPERM` ⇒ treat as alive (fail-closed), and adds failure-path tests.

### Existing Patterns to Follow
- **Reaper-never-throws idiom**: every reaper-adjacent helper wraps `process.kill` in `try/catch` and swallows errors so no exception reaches `reapAndExit`'s poll. `killActiveChildren` uses nested try/catch (`src/engine/active-child.ts:32-40`); `anyChildAlive` uses a single try/catch (`src/engine/active-child.ts:49-54`). The new probe must keep this — but SPEC requires distinguishing `EPERM` (⇒ treat as alive, `return true`) from `ESRCH`/other (⇒ keep checking). Node throws errors carrying a `.code` string (`"ESRCH"`, `"EPERM"`) and an `.errno`; inspecting `err.code` is the discrimination point. The current code does not branch on `.code` at all — it swallows uniformly — so a `.code`-aware branch is new to this module.
- **Group target convention**: negative pid = process group. `killActiveChildren` already uses `-pid` (`src/engine/active-child.ts:33`); the test suite uses `process.kill(-pid, "SIGKILL")` for cleanup (`tests/engine/active-child.test.ts:68, 94`). The change aligns `anyChildAlive` to the same `-pid` form.
- **Group-leader registration**: children are spawned `detached: true` (own process group) in `exec-spawn` and `exec-bash`; the registry records the leader PID. Module header comment: `src/engine/active-child.ts:1-7`.
- Failure handling: today `anyChildAlive` treats *all* probe errors identically (any throw ⇒ "dead, keep checking") — `src/engine/active-child.ts:52-54`. No timeout/retry logic exists in this module; the bounded poll + SIGKILL backstop live entirely in `reapAndExit` (`src/cli/run-one.ts:46-60`) and are out of scope.
- Observability: this module emits **no** structured `.cycle/log.jsonl` events and does no logging. The only adjacent stderr write is `reapAndExit`'s `deps.write(...)` interruption line (`src/cli/run-one.ts:39`). The planner should not add events here — the module is intentionally side-effect-free apart from signalling.
- Idempotency / retry-safety: `register`/`unregister` are idempotent via the `Set` (double-register/unregister are no-ops — proven at `tests/engine/active-child.test.ts:32-48`). `anyChildAlive` is a read-only probe with no state mutation; it is inherently retry-safe and is *called repeatedly* by the poll (`src/cli/run-one.ts:46-51`), so it must remain cheap and non-throwing.

## Open Questions
- **EPERM discrimination mechanism**: SPEC mandates `EPERM ⇒ true`, `ESRCH ⇒ not-alive`, other-error ⇒ must not escape. The current code swallows uniformly with no `.code` inspection. The planner must decide the exact branch shape (e.g. inspect `(err as NodeJS.ErrnoException).code === "EPERM"` ⇒ `return true`; `"ESRCH"` ⇒ continue; any other unexpected error ⇒ per Requirements "must likewise not escape" — i.e. swallow/continue without returning alive). Whether an "other error" should be treated as alive (fail-closed) or as not-alive is constrained by SPEC: Requirements say only ESRCH-gone and EPERM-alive are specified explicitly and "any other unexpected error must likewise not escape"; the acceptance criteria only test ESRCH/EPERM/empty/mixed — the planner resolves the residual-error disposition.
- **Whether to add a per-file coverage floor** for `src/engine/active-child.ts` to `scripts/coverage-gate.mjs` is not requested by the SPEC; absent direction, the planner should rely on the aggregate floors and only ensure no regression.
