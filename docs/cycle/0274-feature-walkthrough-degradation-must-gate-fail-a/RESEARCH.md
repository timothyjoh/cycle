# Research: Cycle 0274

## Cycle Context
SPEC.md requires promoting the walkthrough degradation signal from a non-blocking flag into a **fail-closed blocking gate** on the `feature` workflow's `walkthrough_capture` step. When an explicit, defensively-coerced `engine.walkthrough_required` config is `true`, the cycle ships UI (not doc-only via `expects_code: false`, not opted out via a new per-issue `expects_ui: false` frontmatter field), the walkthrough hook is present-and-ran (exit 0), and a hook-owned degradation sidecar `<artifactDir>/walkthrough/walkthrough-status.json` reports `{ degraded: true }` (or is present-but-unparseable, fail-closed), the engine must route the step through its **existing** fatal step-failure block (`step.end { status: "failed" }` → `cycle.end { status: "failed", failing_step: "walkthrough_capture" }`), emit `walkthrough.degraded { cycle_id, step, reason, sidecar }` exactly once, and surface a `formatWalkthroughDegradedError`-style stderr diagnostic. Every other path — no hook, not opted in, doc-only, `expects_ui: false`, clean/absent sidecar, default-off config — must be byte-for-byte unchanged. The change is engine-only: a new pure resolver module plus a wire-in to the existing `walkthrough_capture` intercept.

- **The existing fatal step-failure block** to reuse: `src/engine/run-cycle.ts:529-542` — emits `step.end { status: "failed", exit_code, duration_ms, stderr }`, then `cycle.end { status: "failed", failing_step: step.name }`, then `return { cycleId, artifactDir, status: "failed", failingStep: step.name }`. ### Existing Patterns to Follow
- **Pure classifier module (the SPEC's model)**: `src/engine/verify-counts.ts:1-104` and `src/engine/noop-marker.ts:1-51`. Both are module-level-regex/parse, never-throw, discriminated-return-type, side-effect-free pure halves with a separate fail-closed async reader. `classifyWalkthroughDegradation(sidecarText)` should mirror `parseNoopMarker` (pure, never throws) with a `classifyNoopMarker`-style reader (`src/engine/noop-marker.ts:43-51` — `readFile` in `try/catch`, absent/unreadable ⇒ fail-closed). Note the SPEC's fail-closed direction is the **inverse** of noop's: an absent sidecar ⇒ **not degraded** (the hook ran and didn't flag), but a present-but-unparseable sidecar ⇒ **degraded** (corrupt proof cannot be coerced to "works").
- **Defensive `=== true` flag coercion at the read site**: `engine.compress_output` is the named convention (`src/engine/workflow.ts:48-51`); the gate read site for `engine.walkthrough_required` resolves `cfg.engine.walkthrough_required === true` (absent/non-boolean/malformed ⇒ `false`). Config flows through `loadConfig` by pass-through — `return parsed as CycleConfig` (`src/engine/workflow.ts:195`); no explicit parse line is added for it, only the `EngineConfig` type field. Compare the `walkthrough_hook_timeout_ms` read-site coercion already in the intercept (`src/engine/run-cycle.ts:518-521`).
- **Frontmatter parsing**: `parseFrontmatter(body)` — `src/engine/frontmatter.ts:11-17`. Throws `"no frontmatter"` when the `---\n…\n---\n` block is absent (so the surrounding read must stay inside the existing `try/catch`). YAML-parsed `fm` is `Record<string, FrontmatterValue>`.
- **Diagnostic-message formatters**: `formatWalkthroughTimeoutError` (`src/engine/run-cycle.ts:324`), `formatVerifyUnverifiedError` (`src/engine/run-cycle.ts:328`), `formatEmptyDiffGuardError` (`src/engine/run-cycle.ts:312`) — exported pure string builders. A new `formatWalkthroughDegradedError` (referenced by the SPEC) belongs here, producing "walkthrough did not demonstrate the feature: …".
- **Head-capping stderr**: `truncateHeadCapped(stderr, MAX_STEP_END_STDERR)` with `MAX_STEP_END_STDERR = 2000` (`src/engine/run-cycle.ts:302`, applied at `src/engine/run-cycle.ts:531-532`).
- **Failure handling (existing, in the change area)**:
  - Non-zero hook exit / timeout ⇒ fatal block (`src/engine/run-cycle.ts:529-542`); the `finally` checkout/base-pull cleanup still runs on the early `return`.
  - Post-success collect/manifest-write failure ⇒ best-effort degrade: `step.walkthrough_capture_failed { cycle_id, step, artifact, error }` (`src/engine/run-cycle.ts:550-557`), step stays `ok`, pointer omitted, cycle outcome unchanged. This degrade path is **explicitly preserved** by the SPEC and must remain after the gate.
  - `execWalkthroughHook` itself never rejects — an unresolved shell / spawn error / non-zero exit all resolve to a `StepResult` with `status: "failed"` (`src/engine/walkthrough.ts:91-93,125-128`).
- **Observability conventions (`.cycle/log.jsonl` structured events)**: every state transition is a `log.emit(eventName, payload)` call with `cycle_id` always present and `step` on step-scoped events. Existing walkthrough events: `step.start { cycle_id, step, agent:"bash" }` (`src/engine/run-cycle.ts:512`), `step.end` variants (`:503,533,558`), `step.walkthrough_capture_failed` (`:551`). The new `walkthrough.degraded { cycle_id, step, reason, sidecar }` follows this shape and must fire **exactly once** before the fatal `step.end`.
- **Exactly-once event discipline (project rule)**: assert with `filter(predicate).length === 1`, not `find` (CLAUDE.md → *Test conventions*; canonical helper `expectExactlyOne(events, eventName)` in `tests/helpers.ts`). The SPEC's AC requires `walkthrough.degraded` be cardinality-pinned this way.
- **Idempotency / retry-safety**: the intercept is re-invoked on every cycle attempt with the same deterministic `CYCLE_ARTIFACT_DIR`/`walkthrough/` paths (media is last-write-wins; re-run safety is the hook author's responsibility — docs/ENGINE.md:333). A gated-degraded failure routes through the standard `max_cycle_attempts` retry / terminal-drain path (no new halt reason); the SPEC requires the same.

## Open Questions
- **Exact `walkthrough.degraded.reason` strings**: the SPEC requires the `reason` to name the parse failure on the unparseable-sidecar path and to reference the sidecar's `reason` field on the `{ degraded: true }` path, but does not fix the exact string vocabulary (e.g. a `"degraded_flag"` vs `"unparseable"` discriminator). The planner should define the precise `reason` values and the `sidecar` field's content (relative vs absolute path).
- **Sidecar JSON shape beyond `degraded`/`reason`**: the SPEC fixes `{ degraded: boolean, reason?: string }`; whether `classifyWalkthroughDegradation` should surface the hook-supplied `reason` distinctly from a parse-failure reason in its return type is a small design choice for the planner.
- **Ordering of the UI-scope read relative to the sidecar classify**: whether to short-circuit (skip the issue read and sidecar parse) when `walkthrough_required !== true` for zero added I/O on the default-off path — implied by "byte-for-byte unchanged" but the planner should pin the guard order (config check first).
- **New resolver module filename and the coverage-floor table entry**: the SPEC names the functions but not the module path; the planner should choose the path and register its `FLOORS` entry in `scripts/coverage-gate.mjs` (≥95%).
