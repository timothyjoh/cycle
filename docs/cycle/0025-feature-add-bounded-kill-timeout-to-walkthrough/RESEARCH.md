# Research: Cycle 0025

## Cycle Context
This cycle adds a config-gated, bounded-kill wall-clock timeout to `execWalkthroughHook` in `src/engine/walkthrough.ts`. The end-of-`feature` `walkthrough_capture` step spawns a repo-provided hook that currently resolves only on the child's `close`/`error` events — there is no timeout, so a hung hook (headless browser, `wait-on` that never resolves, video recorder) blocks `runCycle` and the entire engine indefinitely with no observable signal. The change mirrors the SIGTERM→SIGKILL process-group escalation in `src/engine/exec-spawn.ts`: `execWalkthroughHook` gains a timeout parameter plus an injectable timer seam; on expiry it kills the process tree, marks the resolved `StepResult` with `timedOut: true`, and the `run-cycle.ts` call site reads a new defensively-coerced `engine.walkthrough_hook_timeout_ms` config and routes a timed-out hook through the existing fatal step-failure path with timeout-specific stderr wording. Non-timeout success/failure behavior, media collection, manifest writing, and the best-effort degrade path are untouched.

### Existing Patterns to Follow

- **SIGTERM→SIGKILL process-group escalation (reference implementation)** — `src/engine/exec-spawn.ts:71-87`. `runAgent` spawns with `detached: true` (`src/engine/exec-spawn.ts:29`) so the child is its own process group; `killTree(sig)` calls `process.kill(-child.pid, sig)` with a `child.kill(sig)` fallback in a try/catch (`src/engine/exec-spawn.ts:71-74`). On timeout it sets `timedOut = true`, sends `SIGTERM`, schedules `SIGKILL` after a fixed **5_000 ms** grace period, and `.unref()`s both timers (`src/engine/exec-spawn.ts:80-86`). `execWalkthroughHook` currently spawns **without** `detached: true` (`src/engine/walkthrough.ts:42-46`), so process-tree kill requires adding that option to match the reference.
- **`settled`/`done` single-resolve guard** — `exec-spawn.ts` uses a `settled` boolean and a `done(r)` helper that clears both timers before resolving, so `close`/`error`/timeout cannot double-resolve — `src/engine/exec-spawn.ts:48-57`. `execWalkthroughHook` currently resolves the Promise directly in each handler with no guard (`src/engine/walkthrough.ts:51-57`).
- **`timedOut` result shape on close** — `exec-spawn.ts` resolves `{ status: "failed", exitCode: code ?? -1, stdout, stderr, timedOut: true }` when `timedOut` is set, else the normal ok/failed shape — `src/engine/exec-spawn.ts:60-64`.
- **`timeoutMs` option & arm-only-when-positive guard** — `RunAgentOptions.timeoutMs?: number` documented as "0/undefined disables" (`src/engine/exec-spawn.ts:16-19`); armed only under `if (timeoutMs && timeoutMs > 0)` (`src/engine/exec-spawn.ts:75`).
- **Defensive read-site coercion (the convention to mirror)** — `max_rate_limit_retries` is coerced at the `run-cycle.ts` read site: `typeof rawCap === "number" && Number.isInteger(rawCap) && rawCap > 0 ? rawCap : 24` — `src/engine/run-cycle.ts:478-484`. SPEC requires `walkthrough_hook_timeout_ms` to follow this exact shape (non-integer/`≤0`/`NaN`/`Infinity`/non-number/absent ⇒ disabled; valid positive integer arms; a non-zero default when present-but-honoring the malformed rule). `compress_output === true` (`src/engine/run-cycle.ts:456`) is the boolean-coercion analog.
- **Injectable timer/clock seams** — `RunCycleOpts.sleepFn` and `nowFn` are injected with real-clock defaults at `src/engine/run-cycle.ts:249-250` and `src/engine/run-cycle.ts:293-294`. SPEC requires the new timeout timer in `execWalkthroughHook` to accept an injectable seam so tests do not depend on wall-clock.
- **Timeout-specific failure wording** — `formatTimeoutProofError(stepName, artifactPath, exitCode)` returns `<step> timed out (exit <code>) and left <artifact> empty — treating as failure`, distinct from `formatCompletionProofError` — `src/engine/run-cycle.ts:203-209`. The completion-proof path already branches on `r.timedOut` to choose between them at `src/engine/run-cycle.ts:587-588`. SPEC asks the new walkthrough timeout stderr to parallel this wording and reference the actual signal/exit code (a SIGTERM-killed child typically reports `exit_code: 143`).

- **Failure handling (existing in the change area)**: the walkthrough fatal path emits `step.end { status: "failed", exit_code, duration_ms, stderr }` (stderr head-capped via `truncateHeadCapped(wr.stderr, MAX_STEP_END_STDERR)`), then `cycle.end { status: "failed", failing_step: step.name }`, and returns `{ cycleId, artifactDir, status: "failed", failingStep: step.name }` — `src/engine/run-cycle.ts:371-382`. `MAX_STEP_END_STDERR = 2000` at `src/engine/run-cycle.ts:189`. The early return still flows through the `finally` checkout/base-pull cleanup (documented behavior). `execWalkthroughHook`'s spawn-error handler resolves a failed `StepResult` rather than rejecting (`src/engine/walkthrough.ts:51`) — must be preserved.
- **Observability conventions**: structured JSONL events emitted via `log.emit(eventName, payload)` to `.cycle/log.jsonl`. Walkthrough events in scope: `step.start { cycle_id, step, agent: "bash" }` (`src/engine/run-cycle.ts:366`), `step.end` (skipped/ok/failed variants at `:357-363`, `:397-404`, `:372-379`), `cycle.end` (`:380`), and the best-effort `step.walkthrough_capture_failed { cycle_id, step, artifact, error }` (`:390-395`). Durations computed as `Math.max(0, Math.round(nowFn() - stepStart))`.
- **Idempotency / retry-safety**: no lock or dedup in the walkthrough step itself; the engine re-invokes the step on every cycle attempt with the same deterministic `CYCLE_ARTIFACT_DIR`/`walkthrough/` paths (last-write-wins, hook author's responsibility — `docs/ENGINE.md:211`). The single-resolve `settled` guard from `exec-spawn.ts` is the relevant retry-safety mechanism to add so timeout + `close` do not double-resolve.
