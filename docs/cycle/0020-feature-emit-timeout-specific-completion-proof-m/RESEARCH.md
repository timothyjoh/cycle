# Research: Cycle 0020

## Cycle Context
SPEC.md asks for a timeout-aware completion-proof failure message. Today the `"nonempty"` proof policy in `src/engine/run-cycle.ts` stamps the hard-coded `formatCompletionProofError` text — `"<step> exited 0 but <artifact> is empty — treating as failure"` — onto `step.end.stderr` for *every* empty-artifact failure, including steps that were SIGTERM-killed at the timeout limit (`r.timedOut === true`, `exit_code: 143`). That produces a self-contradictory `step.end` record (exit code 143 paired with stderr claiming the step "exited 0"). This cycle adds a new pure formatter (e.g. `formatTimeoutProofError(stepName, artifactPath, exitCode)`) and branches the `"nonempty"` proof message on `r.timedOut`: timed-out empty artifacts get timeout-specific wording referencing the real exit code; the genuine `r.status === "ok"` exit-0 path keeps the existing wording. The failure→retry routing, the `step.completion_check` status logic, the `step.timeout`/`step.timeout_salvaged` events, and `max_cycle_attempts` accounting are all unchanged — only the `r.stderr` string value differs on the timed-out-empty path.

### Existing Patterns to Follow
- **Pure greppable formatter**: every guard message is produced by an exported, single-expression template-literal function (`format*Error`) with no side effects — `src/engine/run-cycle.ts:183-197`. The new `formatTimeoutProofError(stepName, artifactPath, exitCode)` must match this shape. The SPEC's suggested text is `"<step> timed out (exit 143) and left <artifact> empty — treating as failure"` and must **not** contain the substring `"exited 0"`.
- **Proof-policy branching**: the `proof` switch (`spec-min-bytes` / `fix-conditional` / `nonempty`) at `src/engine/run-cycle.ts:497-512` sets a local `proofError: string | null`. The new branch belongs inside the `"nonempty"` arm (lines 508-511): when the artifact is empty, choose `formatTimeoutProofError(...)` if `r.timedOut`, else `formatCompletionProofError(...)`. The downstream `if (proofError)` handler (lines 519-522) is reused verbatim.
- **Failure routing (must stay byte-for-byte equivalent)**: a non-null `proofError` sets `r.status = "failed"`, `r.exitCode = r.exitCode || 1`, `r.stderr = proofError` (`src/engine/run-cycle.ts:519-522`), then falls through to the shared `step.end` → `cycle.end status:"failed"` → early `return` at `src/engine/run-cycle.ts:589-613`. The change only alters the *value* assigned to `r.stderr`. Note `r.exitCode` on the timed-out path is already non-zero (143 empirically), so `r.exitCode || 1` is a no-op there.
- **Salvage path (must stay unchanged)**: when the artifact passes its proof but `r.timedOut`, the `else if (r.timedOut)` branch sets `r.status = "ok"` and emits `step.timeout_salvaged` — `src/engine/run-cycle.ts:523-529`. The new message branch only fires when `proofError` is non-null (artifact empty), so it never interacts with salvage.
- **Failure handling today**: an empty/whitespace artifact (whether clean exit-0 or timeout-killed) is a *retryable* step failure routed through the unchanged `max_cycle_attempts` machinery; nothing is swallowed. Timeouts are bounded by `engine.step_timeout_ms` (default `2700000`, `src/defaults/workflows.yml:8`); on expiry the child's process group is SIGTERM-then-SIGKILL killed (`src/engine/exec-spawn.ts:71-87`). No automatic re-run inside `runCycle` for timeouts — the failure propagates up to the supervisor's retry loop.
- **Observability conventions**: structured NDJSON events to `.cycle/log.jsonl` via `log.emit(event, payload)`. Relevant events around the change: `step.timeout { cycle_id, step, limit_ms }`, `step.completion_check { cycle_id, step, artifact, status }`, `step.timeout_salvaged { cycle_id, step, artifact }`, `step.end { …, exit_code, stderr }`. No new event may be introduced by this cycle; no existing event's emission count may change (SPEC requirement + the repo's exactly-once cardinality rule).
- **Idempotency / retry-safety**: no locks or dedup keys in the proof block itself — it is a pure post-condition on a single `StepResult`. `classifyArtifact` fails closed (unreadable ⇒ `"empty"`). The exactly-once contract for `step.completion_check` and `engine.halted`/`reflection.summary` (CLAUDE.md "Test conventions") must be preserved; the planner must assert cardinality with `filter(predicate).length === 1`, not `find`.

## Open Questions
- **Exit-code source on timeout**: empirically the timed-out `review` step recorded `exit_code: 143` (`.cycle/log.jsonl`, cycle 0019), yet `src/engine/exec-spawn.ts:62` resolves `exitCode: code ?? -1` and the `close` handler captures only `code` (not `signal`). The claude CLI evidently installs a SIGTERM handler that exits 143, but the codebase does not hard-code 143. The planner should decide whether `formatTimeoutProofError` interpolates the actual `r.exitCode` (robust to any signal-derived code) rather than literal `143` — the SPEC requirement ("references the actual exit code") and the example text (`exit 143`) point to interpolation. A test asserting the exact string must therefore feed a known exit code, or assert on `/timed out/` + absence of `exited 0` rather than the literal `143`.
- **Timeout simulation in `runCycle` tests**: the existing `workflowYml` helper emits no `step_timeout_ms`. The planner must confirm the smallest reliable timeout value and a fake-`claude` hang recipe (e.g. `sleep N` with `N` ≫ timeout) that deterministically yields `r.timedOut === true` with an empty artifact under the test runner's timing, without flaking on slow CI.
- **Whether to keep a dedicated `formatTimeoutProofError` unit test** mirroring the existing `formatCompletionProofError` unit test (`run-cycle.completion-proof.test.ts:109-113`) in addition to the end-to-end `runCycle` assertion — the SPEC requires both the new branch and the unchanged branch be asserted, but does not mandate the formatter's unit-level test explicitly.
