# Research: Cycle 0009

## Cycle Context
SPEC.md asks the engine to enforce a per-step completion-proof contract in `src/engine/run-cycle.ts`. Today an agent step is treated as successful on exit code 0 alone; the engine then writes whatever the step produced to `<artifactDir>/<STEP>.md` without checking that the file has content. The cycle requires a single declarative step→artifact table that, after any agent step exits 0, verifies the declared artifact is non-empty (not missing, not 0 bytes, not whitespace-only), converts an empty result into the same kind of failure a non-zero exit produces (so it routes through the existing retry / `max_cycle_attempts` machinery), and emits a `step.completion_check { step, artifact, status }` event to `.cycle/log.jsonl` for each checked step. Bash steps and agent steps that declare no artifact are out of scope.

## Current Codebase State

### Existing Patterns to Follow
- **Post-condition guard pattern (the exact pattern the new check should mirror).** After the artifact write, existing guards re-open the `r.status === "ok"` branch, compute a condition, and on failure set `r.status = "failed"`, `r.exitCode = r.exitCode || 1`, and `r.stderr = <descriptive message via a format helper>`. Three live examples:
  - spec min-bytes guard — `src/engine/run-cycle.ts:376-383`, message via `formatSpecGuardError` (`src/engine/run-cycle.ts:151-153`), threshold `SPEC_MIN_BYTES = 200` (`src/engine/run-cycle.ts:148`).
  - fix-vs-MUST-FIX guard — `src/engine/run-cycle.ts:384-394`, message via `formatFixGuardError` (`src/engine/run-cycle.ts:155-157`).
  - build/fix empty-diff guard — `src/engine/run-cycle.ts:395-410`, message via `formatEmptyDiffGuardError` (`src/engine/run-cycle.ts:159-161`).
  Each guard is gated on `r.status === "ok"` so a prior guard's failure is not overwritten. The new completion check would compose with these (SPEC asks the new declarative table to subsume/consolidate the scattered guards).
- **Exported format-helper convention.** Error message strings are produced by small exported pure functions (`formatSpecGuardError`, `formatFixGuardError`, `formatEmptyDiffGuardError` — `src/engine/run-cycle.ts:151-161`) so tests can assert message shape without duplicating literals. The SPEC-mandated message is `"<step> exited 0 but <artifact> is empty — treating as failure"`.
- **Declarative step-set constants.** Step membership is expressed as module-level `Set<string>` constants (`RESET_ELIGIBLE_STEPS`, `SKIP_ELIGIBLE_STEPS`, `ARTIFACT_STEPS` — `src/engine/run-cycle.ts:27-35`); some are exported (`RESET_ELIGIBLE_STEPS`) for test import (`tests/engine/run-cycle.test.ts:7`). A new declarative step→artifact table would follow this convention.
- **Artifact path derivation.** `join(artifactDir, \`${stepName.toUpperCase()}.md\`)` is the canonical mapping from step name to artifact file, used at `src/engine/run-cycle.ts:138` and `:374`. There is currently no placeholder substitution of `{cycle_id}`/`{slug}` — paths are derived purely from step name and `artifactDir`. `artifactDir` itself is `docs/cycle/<cycleId>-<workflow>-<slug>` built in `src/engine/branch.ts:36, 44, 59`.
- **Failure handling (how a failed step flows today).** After post-processing, `step.end` is emitted with `status`, `exit_code`, and (on failure) head-capped `stderr` — `src/engine/run-cycle.ts:430-438`. Then on `r.status === "failed"`: `reflection` and `documentation` are non-fatal (`reflection.skipped` / `documentation.skipped`, then `continue` — `src/engine/run-cycle.ts:440-447`); any other failing step emits `cycle.end {status:"failed", failing_step}` and returns `{status:"failed", failingStep}` (`src/engine/run-cycle.ts:448-449`). Upstream, `run-one.ts` exits non-zero (`src/cli/run-one.ts:92`), and `cli.ts` reads `failing_step` from the log (`src/cli.ts:284-307`), then either retries (`drainFailedRetry`, attempt bumped, `cycle_id` preserved — `src/engine/queue.ts:234-247`) or terminal-drains at `attempt+1 >= max_cycle_attempts` (`src/cli.ts:553-567`). `max_cycle_attempts` default 3 (`src/defaults/workflows.yml:25`). A completion-check failure that sets `r.status = "failed"` on a fatal step automatically inherits this path.
- **Observability conventions.** All events go through `log.emit(event, fields)` which appends one JSON line `{ts, event, ...fields}` to `.cycle/log.jsonl` and echoes to stdout — `src/engine/log.ts:8-18`. Engine events carry `cycle_id` and (for step events) `step`. Existing per-step events: `step.start` (`:312-317`), `step.end` (`:430-438`), `step.skipped` (`:260-265`), `step.warning` (`:297-332`). A new `step.completion_check { step, artifact, status }` would match this shape; the SPEC requires `status` discriminating `"pass"`/`"fail"`.
- **Exactly-once event assertion rule.** Per CLAUDE.md and `tests/helpers.ts:3-10` (`expectExactlyOne`), events asserted as exactly-once must be cardinality-pinned with `filter(predicate).length === 1`, not `find`. The SPEC's acceptance criteria explicitly require `step.completion_check` presence to be asserted this way.
- **Idempotency / retry-safety.** Retry reuses the same `cycle_id` and therefore the same `artifactDir` (`src/engine/queue.ts:240-244`), so artifacts from a prior attempt persist on disk. The retry-skip gate (`src/engine/run-cycle.ts:257-268`) skips `spec/research/plan` when their `<STEP>.md` is `> 0` bytes — meaning a non-empty artifact left by a prior attempt is treated as completed. A new completion check must not conflict with this (a step that passed the non-empty check and was committed would, on retry, be skip-eligible only if in `SKIP_ELIGIBLE_STEPS`). Resume index math (`src/cli.ts:379-386`) treats a step as completed when its name appears in the tail's completed steps; `parseLogTail` treats `step.skipped` as ok-equivalent.
- **Artifact sanitization.** `sanitizeArtifactStdout(r.stdout)` (`src/engine/sanitize-artifact.ts`, called at `src/engine/run-cycle.ts:373`) is applied before write; the byte/whitespace content the completion check would inspect is the post-sanitization content. The spec guard already measures `Buffer.byteLength(sanitized, "utf8")` (`src/engine/run-cycle.ts:377`).

## Open Questions
- **Relationship between the new step→artifact table and `ARTIFACT_STEPS`.** SPEC requires "one declarative table (single source of truth)" that consolidates existing scattered guards. Whether the new table replaces `ARTIFACT_STEPS` (currently also used at `src/engine/run-cycle.ts:323` to decide File-Artifact-Mode prompt suppression) or sits alongside it must be decided by the planner. `reflection` is an agent step that produces `REFLECTION.md` but is non-fatal and is *not* in `ARTIFACT_STEPS`; the planner must decide whether it is subject to the completion check (SPEC scope says only agent steps that *declare* an artifact).
- **Whether the table keys on step name (current derivation `name.toUpperCase()+".md"`) or introduces an explicit per-step `artifact` field on `Step`.** The codebase derives artifact paths from step name today (`src/engine/run-cycle.ts:138, 374`); SPEC phrasing ("step→artifact mapping table") does not mandate a config-schema change.
- **Interaction with the spec guard's existing 200-byte floor and the fix-guard's whitespace check.** SPEC says fold existing per-step guards into the table "rather than left duplicated." The spec guard fails below 200 bytes (stricter than non-empty), and the fix guard already treats whitespace-only as empty when MUST-FIX has tasks. The planner must reconcile precedence so the completion check and these stricter/conditional guards do not double-report or weaken each other.
- **Placement relative to the artifact write and other guards.** The artifact is written unconditionally at `src/engine/run-cycle.ts:375` before the guards; the completion check must read what was written (or the in-memory sanitized string) and run while `r.status === "ok"`, consistent with the existing guard ordering.
