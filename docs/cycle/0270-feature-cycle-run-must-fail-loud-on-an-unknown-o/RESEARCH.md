# Research: Cycle 0270

## Cycle Context
SPEC.md asks to close a false-green in `cycle run`: when invoked with an unknown or value-less `--workflow`, the run path never validates `args.workflow` against the loaded config's workflow set, so engine-start `runPreflight` passes (a missed `findWorkflow` lookup silently narrows the agent/tool probe set), the issue is marked in-progress, and the run only fails deep inside `runCycle` with an opaque `unknown workflow: <name>` throw that `run-one` maps to a generic exit 2 — burning the full `max_cycle_attempts` (3) budget on identical retries before parking the issue in `failed/`. The fix factors out the validation logic `cycle doctor` already carries (cycle 0266) into a single shared helper returning a discriminated result, wires it into the `cycle run` start path **before** `markInProgress`/`runPreflight`, and wires it into both resume entrypoints — so an unknown/value-less `--workflow` fails loud (stderr naming the bad value + listing available workflows) and exits non-zero with zero state mutation, identically across `run` and `doctor`.

### Existing Patterns to Follow
- **Discriminated-result helper shape**: SPEC requests `{ ok: true, name }` vs `{ ok: false, message }`. The existing `runDoctor` returns the parallel `DoctorResult = { stdout; stderr; exitCode }` (`src/cli/doctor.ts:4`) and `runPreflight` returns a discriminated `PreflightResult` (`src/engine/preflight.ts`, imported `src/cli/doctor.ts:2`) — the repo already models command outcomes as plain typed result objects the caller acts on, never throwing for expected-bad input.
- **Doctor arg-parsing parity (the model for value-less detection)**: the `doctor`/`preflight` dispatch in `src/cli.ts:117-129` manually indexes `rest.indexOf("--workflow")` (`:120`) and computes `workflow = rest[wfIdx + 1] ?? ""` (`:125`) — flag absent ⇒ `undefined`; flag present, no value ⇒ `""`; this is the exact distinction the run path must replicate (SPEC Requirements). `runDoctor` then keys on `undefined`/`""`/unknown (`src/cli/doctor.ts:83-99`).
- **`undefined` ⇒ default-`feature` semantics**: `DoctorOpts.workflow` is documented as `undefined ⇒ no flag ⇒ default feature (no rejection possible)`; an explicit string (incl. `""`) is user-supplied and validated (`src/cli/doctor.ts:8-14, 83-86`).
- **Config-load failure preservation**: `runDoctor` wraps `loadConfig` in try/catch and returns a non-zero stderr result (`src/cli/doctor.ts:64-74`); the run path loads config plainly at `src/cli.ts:293` (loadConfig's own error path is the existing config-load failure surface to preserve — validation runs only after a successful load).
- **Failure handling**: the unknown/value-less `--workflow` IS the failure surface. The established convention is write to stderr + non-zero exit (`console.error` + `process.exit(code)` pattern at the lock-failure site `src/cli.ts:221-229`, and the doctor dispatch `process.exit(result.exitCode)` at `src/cli.ts:129`). The helper itself must not throw for any string/empty/undefined input (SPEC) — mirroring `runDoctor`'s "never throws" contract (`src/cli/doctor.ts:60`).
- **Observability**: structured events go to `.cycle/log.jsonl` via `log.emit(...)` (created at `src/cli.ts:233`). The rejection must occur **before** `createLogger`/`engine.start` mutate the log? — note `createLogger` is at `src/cli.ts:233` and `engine.start` at `src/cli.ts:299`, both **after** `loadConfig` (`:293`). Acceptance criterion requires "no new `cycle.start`/in-progress mutation"; `cycle.start` is emitted inside `runCycle`/`run-one`, well after the proposed gate, and `markInProgress` (`:602`/`:863`) is also after it — so a gate placed right after `:293` and before `:344` satisfies "no issue marked in-progress." (The lock at `src/cli.ts:218-231` is acquired earlier and released on `process.on("exit")` at `:231` — an early `process.exit` still releases it.)
- **Idempotency / retry-safety**: the PID-lockfile (`acquireLock`/`releaseLock`, `src/cli.ts:218-231`, `src/engine/engine-lock.ts`) is the single-engine guard; it is acquired before config-load, so a rejected workflow exits with the lock cleanly released (no in-progress mark, no `cycle.start`). `markInProgress` (`src/engine/issue-lifecycle` import region `src/cli.ts:14`) is the in-progress state mutation the gate must precede.
