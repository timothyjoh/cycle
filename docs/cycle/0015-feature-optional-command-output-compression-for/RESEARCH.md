# Research: Cycle 0015

## Cycle Context
SPEC.md asks for an **opt-in command-output compression path for `claudecode` steps** to reduce context-window token spend on verbose read-command output (`git`, `ls`, `grep`, `diff`, `cat`, …). Two pieces are in scope: (1) a new `cycle compress-output -- <cmd>...` CLI subcommand that spawns the command with array args (no shell), captures stdout/stderr, and — when stdout exceeds a configurable byte threshold — applies a deterministic density filter (retain head + tail lines plus all stderr/error lines, elide the middle with a `[… N lines/B bytes elided …]` marker), passing through verbatim below threshold while always preserving the child's exit code; and (2) opt-in wiring via a new `engine.compress_output` config flag (default `false`) that, when true, registers a `PreToolUse` hook in the **claude lane only** (`exec-claudecode.ts`, via the claude CLI `--settings`/hook mechanism) to rewrite allowlisted shell-operator-free read commands through `cycle compress-output`. With the flag off (the default), `claudecode` invocation must be byte-for-byte identical to current behavior. The hook must fail open (errors leave the original command running). Non-claude agents (`codex`, `gemini`, `auggie`, `opencode`, `pi`, `bash`) are out of scope.

### Existing Patterns to Follow
- **Subcommand handler pattern**: each command in `src/cli.ts:46-109` is a top-of-file `if (argv[0] === "<name>")` guard that dynamically imports a handler from `src/cli/<name>.ts`, writes `result.stdout`/`result.stderr`, and calls `process.exit(result.exitCode)`. Handlers returning `{ stdout, stderr, exitCode }` (see `triage` at `cli.ts:65-71`, `cleanup` at `cli.ts:80-86`) are the convention; `compress-output` would naturally add a guard here plus a `src/cli/compress-output.ts` module. Note: `--` would land in `argv`; existing handlers slice `argv.slice(1)`.
- **Subprocess discipline (array args, never shell)**: `spawn`/`spawnSync` with array args and `shell: false` everywhere. Canonical examples: `spawnRunOne` at `src/cli.ts:266-293` (`spawn(process.execPath, [process.argv[1], "run-one", ...args], { env: buildChildEnv(extra), stdio: "inherit", shell: false })`); `runAgent` at `src/engine/exec-spawn.ts:40-43` (`spawn(binary, finalArgv, { ...base, shell: false })`); `git status --porcelain` calls in `run-cycle.ts:100-104` / `131-135` use `spawnSync(..., { shell: false })`.
- **StepResult shape** (returned by agent/bash exec): `{ status: "ok" | "failed"; exitCode: number; stdout: string; stderr: string; rateLimited?: true; timedOut?: true }` — defined in `src/engine/exec-bash.ts` (imported as `StepResult` by `exec.ts:1`, `exec-spawn.ts:5`). `runAgent` maps `close` → `status: code === 0 ? "ok" : "failed"`, `exitCode: code ?? -1` (`exec-spawn.ts:60-64`); spawn `error` → `{ status: "failed", exitCode: -1, stderr: err.message }` (`exec-spawn.ts:65-67`).
- **Head/tail truncation helper (reuse candidate)**: `truncateHeadCapped(s, max)` at `src/engine/log-fmt.ts:1-3` (`s.length > max ? s.slice(0, max-1) + "…" : s`); `stripFences(s)` at `log-fmt.ts:5-8`. `MAX_STEP_END_STDOUT = 2000` / `MAX_STEP_END_STDERR = 2000` constants live in `src/engine/run-cycle.ts:177-178`.
- **Config boolean coercion convention**: optional engine fields are typed `?:` on `EngineConfig` and read with a defaulting expression at the consumer's read site, not normalized at load time. Pattern for booleans: `cfg?.engine?.skip_completed_on_retry ?? true` (`src/cli.ts:181`). Pattern for "malformed degrades to disabled" (numeric): `min_step_duration_ms` resolved defensively at the read site — `const thresholdMs = typeof rawMin === "number" && Number.isFinite(rawMin) && rawMin > 0 ? rawMin : 0;` (`src/cli.ts:510-513`). The SPEC requires `compress_output` to follow the boolean variant (absent/non-boolean/malformed ⇒ `false`); `loadConfig` itself does no numeric/boolean validation of these fields (`workflow.ts:62-137` only validates structure, `commit.mode`, and the `defaults` block).
- **Failure handling (today)**:
  - Agent step failure routing: `run-cycle.ts:370-389` — `runStep` errors are caught only for `UnknownAgentError` (mapped to a failed `StepResult`); a rate-limited claude result is re-tagged `{ status: "failed", rateLimited: true }` in `exec-claudecode.ts:19` and retried by `run-cycle`'s loop (`exec-spawn` close/error handling at `exec-spawn.ts:60-67`).
  - Timeout: per-step wall-clock via `timeoutMs` → `cfg.engine.step_timeout_ms` (`run-cycle.ts:385`); `runAgent` kills the process group (SIGTERM then SIGKILL after 5s grace) and marks `timedOut: true` (`exec-spawn.ts:75-87`); `step.timeout` event emitted (`run-cycle.ts:409`).
  - Supervisor terminal-failure/halt bookkeeping: `recordTerminalFailure` (`src/engine/halt-accounting.ts`, used at `cli.ts:531-545`, `584-598`, `604-618`); iteration-too-fast fast-bail via `advanceFastFailCounter` (`cli.ts:560-573`). The new feature does not touch these paths.
  - Config errors throw `workflows.yml malformed: … (${path})` (`workflow.ts:71-128`); a thrown `loadConfig` is tolerated by callers that treat absent `cfg` as a no-op (`cli.ts:178,186`).
- **Observability conventions**: structured JSONL events via `log.emit("<namespace>.<event>", { … })` to `.cycle/log.jsonl` (`createLogger` from `src/engine/log.ts`). Existing event names use dotted namespaces: `engine.*`, `cycle.*`, `step.start`/`step.end`/`step.timeout`/`step.warning`/`step.completion_check`/`step.output_capture_failed`, `queue.drained`, `issue.*`. `step.warning` carries `{ cycle_id, step, reason, … }` (e.g. `cli.ts:576-582`, `run-cycle.ts:364-368`). A hook fail-open event, if added, should follow this naming/shape. Direct stdout for CLI subcommands is also conventional (e.g. `status`, `help`).
- **Idempotency / retry-safety**: single-engine PID lockfile via `acquireLock`/`releaseLock` (`src/engine/engine-lock.ts`, used at `cli.ts:145-152`). The compress-output filter is a stateless pure-ish transform over captured bytes; no new locks/dedup needed, but it must remain deterministic (SPEC requirement) and must not alter the child exit code (idempotent passthrough below threshold).

## Open Questions
- **Claude CLI hook/`--settings` surface**: the exact flag and settings-file schema for registering a `PreToolUse` hook (file path vs inline JSON, hook event name, command-rewrite contract) is an external-CLI detail not represented anywhere in this repo; the planner must specify how `exec-claudecode.ts` materializes and points the claude CLI at the hook (e.g. a generated settings file in `.cycle/`, its lifecycle, and cleanup) and how the hook script locates a resolvable `cycle` binary to fail open when it cannot.
- **Filter configurability knobs**: SPEC requires the byte threshold and head/tail keep amounts to be configurable with documented defaults, but does not fix where they live (additional `engine.*` sub-keys, `compress-output` CLI flags, or both) or their default values — the plan must decide and wire defaults.
- **Allowlist + shell-operator detection**: the precise allowlisted binary set and the exact metacharacter denylist (`|`, `>`, `&&`, `;`, `$(`, backticks, `<`, `&`, etc.) for the "conservative rewrite" are sketched in SPEC/issue but not enumerated; the planner must finalize the classification predicate.
- **Per-file coverage floor values** for the new `src/cli/compress-output.ts` (and any hook/classifier helper modules) — choose consistent with existing CLI (70) vs pure-helper (90–100) floors.
- **Whether a structural invariant** should pin the default-off byte-for-byte-identical claude argv contract (optional; the existing `exec-claudecode.test.ts` baseline assertion may suffice).
