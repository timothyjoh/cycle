# Research: Cycle 0263

## Cycle Context
SPEC.md asks for a thin, user-invokable `cycle doctor` subcommand (alias `cycle preflight`) that exposes the **existing** engine-start preflight gate as an on-demand command. It must add `src/cli/doctor.ts` exporting `runDoctor({ cwd, workflow }) → { stdout, stderr, exitCode }` that calls `loadConfig(cwd)` + `runPreflight`, renders the `PreflightResult` (`checks` / `warnings` / `failures`) as a human-readable report on stdout, exits 0 on a clean pass (warnings present or not) and non-zero when any check fails. It must be read-only — acquire no engine lock and mutate no state (`.cycle/`, queue, log, `docs/cycle/**`). Dispatch wiring goes in `src/cli.ts` for `argv[0] === "doctor"` and `argv[0] === "preflight"`, with a `--workflow <name>` pass-through (default `feature`). Usage text, the `CLAUDE.md` commands table, and a `docs/` entry must document it. No probing logic is duplicated — the report is purely a renderer over `runPreflight`'s return value. `runPreflight`, `AGENT_BINARY`, and the engine-start preflight path are explicitly out of scope (no changes).

### Existing Patterns to Follow
- **CLI-module `{ stdout, stderr, exitCode }` convention**: `runCliCleanup` returns `CleanupResult = { exitCode; stdout; stderr }` — `src/cli/cleanup.ts:27-31`. `runCliTriage` and `runUpgrade` follow the same shape. `runStatus` is the simpler variant returning a plain `string` — `src/cli/status.ts:18`. The SPEC specifies `runDoctor` returns `{ stdout, stderr, exitCode }`, matching cleanup/triage/upgrade.
- **`src/cli.ts` dispatch / early-return blocks**: each subcommand is an `if (argv[0] === "<name>")` block that dynamically `import()`s its module, writes `result.stdout`/`result.stderr`, and calls `process.exit(result.exitCode)` — `status` `src/cli.ts:82-87`, `triage` `src/cli.ts:89-95`, `cleanup` `src/cli.ts:104-110`, `compress-output` `src/cli.ts:112-118`, `upgrade` `src/cli.ts:74-80`. These blocks all sit **before** `parseArgs`/lock acquisition (`src/cli.ts:160`, `src/cli.ts:194-196`), so a new `doctor`/`preflight` block placed alongside them naturally avoids `acquireLock` and never mutates state. Output-newline convention varies: `cleanup`/`triage`/`upgrade` append a trailing newline to `stderr` (`src/cli.ts:108`, `:93`, `:78`); `compress-output` writes both streams verbatim (`src/cli.ts:115-116`).
- **`--workflow` parsing**: `parseArgs` already defines `workflow: { type: "string", default: "feature" }` and emits `RunArgs.workflow` — `src/cli/parse-args.ts:46`, `:61`. `parseArgs` rejects any non-`run`/`drop` first token with `unknown command: <argv[0]>` — `src/cli/parse-args.ts:41`, so `doctor`/`preflight` must be dispatched **before** `parseArgs` is called (like the other subcommands) OR registered in `parse-args`. The issue's acceptance criteria says "Registered in `parse-args`, the `cli.ts` dispatch, and the `cycle help` usage text," but the SPEC scopes it as an early-return dispatch block; the existing subcommands (`status`/`cleanup`/etc.) parse their own `argv.slice(1)` flags inside their module rather than going through `parseArgs`. A planner must reconcile: the early-return blocks fire before `parseArgs`, so the doctor block must extract `--workflow` from `argv.slice(1)` itself (defaulting to `"feature"`) unless `parse-args` is extended.
- **Engine-start preflight rendering (the reference renderer to mirror, not reuse)**: `src/cli.ts:278-306` iterates `pf.warnings` → `engine.preflight.warning` events, and on `!pf.ok` emits `engine.preflight.failed { failures: [...] }` + `engine.stop { reason: "preflight_failed" }` + `process.exit(1)`, else `engine.preflight.ok { checks: pf.checks.length }`. The doctor renderer produces human-readable text instead of log events but covers the same data (checks, warnings, failures+fix). The SPEC requires the engine-start path stay byte-for-byte unchanged.
- **`--skip-preflight` bypass**: `args.skipPreflight` (from `parse-args.ts:50`/`:65`) gates the engine-start block — `src/cli.ts:278`. Not applicable to `doctor` (the command *is* the preflight), but documents the existing flag convention.
- **Failure handling (existing approach in the change area)**: `runPreflight` is total — every probe error becomes a recorded failed check (`src/engine/preflight.ts:204-213`, `:230-238`) and any internal throw is caught into a synthetic `internal` failure (`src/engine/preflight.ts:245-254`); it never throws out. The only throw the doctor path must catch is from `loadConfig` (`src/engine/workflow.ts:116`, `:120-135`). The established pattern for surfacing such errors in CLI modules is a non-zero `exitCode` + a message on `stderr` (e.g. cleanup's unknown-flag/error paths return `exitCode: 1` with `stderr` text — `tests/cli/cleanup.test.ts:155`, `:171`).
- **Observability**: structured JSONL events to `.cycle/log.jsonl` via `createLogger` (`src/engine/log.ts`) are the engine's convention, but the doctor command is read-only and **must not** write the log; it prints to stdout/stderr only (matching `status`/`cleanup`/`upgrade`, which likewise do not emit log events). The `engine.preflight.*` events remain exclusive to the engine-start path.
- **Idempotency / retry-safety**: the engine lock (`acquireLock`/`releaseLock`, `src/engine/engine-lock.ts`, acquired at `src/cli.ts:196`) enforces single-engine exclusion. The doctor command must **not** acquire it — it runs while an engine may be running. Being read-only, it needs no dedup key or guard.

## Open Questions
- **`--workflow` plumbing**: the issue's acceptance criteria mention registering in `parse-args`, but the SPEC and every existing subcommand dispatch *before* `parseArgs` runs (which rejects unknown first tokens, `src/cli/parse-args.ts:41`). The planner must decide whether `runDoctor` parses `--workflow` from `argv.slice(1)` itself (matching cleanup/triage) or whether `parse-args` is extended to recognize `doctor`/`preflight` as commands. The existing early-return subcommands do their own flag parsing.
- **Exact report format**: the SPEC's example block (`SPEC.md:28-36`) shows columnar `kind name STATUS path/message` rows ending with a `doctor: N check failed` summary. The precise column widths, alignment, and the pass-marker token (`ok` vs a symbol) are a renderer-formatting choice the plan should pin; the data to include (kind, name, status, resolvedPath, per-failure `fix`, per-warning `message`) is fixed by the requirements.
- **stderr-newline convention**: `cleanup`/`triage`/`upgrade` append a trailing newline to `stderr` at the `cli.ts` call site (`src/cli.ts:78`, `:93`, `:108`) while `compress-output` writes verbatim (`:115-116`); the plan should choose which the doctor dispatch block follows so tests assert the right bytes.
- **Config-load error message wording**: the SPEC asks for a "run `cycle init` first / config could not be loaded" diagnostic; the exact text and whether it forwards `loadConfig`'s own `workflows.yml missing: <path>` message is unspecified — a plan-time decision.
