# Research: Cycle 0007

## Cycle Context
Cycle 0007 fixes a remote-branch-orphaning bug in `pr.sh`: when GitHub auto-merge is disabled and the script falls through to the synchronous `gh pr merge --squash --delete-branch` fallback, `--delete-branch` is silently ignored (it only takes effect when GitHub itself performs the merge via the auto-merge queue). The fix is to add an explicit `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/<branch>` invocation after a successful fallback merge, with the owner/repo resolved at runtime via `gh repo view --json nameWithOwner -q .nameWithOwner`. A failed ref-deletion must warn (`pr.sh:`-prefixed stderr) but still print `${pr_url}` and exit 0 — orphan refs are janitorial, not a quality gate. Static-shape tests must lock in: presence of the DELETE call, textual ordering after the fallback `gh pr merge`, gating on `fallback_rc -eq 0`, and the warn-and-continue contract.

## Open Questions
- Test-file placement: SPEC says "`tests/defaults/pr-auto-merge-fallback.test.ts` (or a sibling test file)". The planner must decide whether to extend the existing 7-assertion file with the new DELETE assertions, or create `tests/defaults/pr-fallback-branch-cleanup.test.ts` (or similar) alongside. Both satisfy the SPEC literally; the conventional pattern in this repo is one feature-area per test file (see `commit-staging.test.ts` vs `scripts.test.ts`), which mildly favors a sibling file but the existing file's name already covers "fallback" semantics.
- DELETE invocation shape: SPEC mandates `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/<branch>` and `gh repo view --json nameWithOwner -q .nameWithOwner` for owner/repo resolution, but does not pin whether the owner/repo lookup happens at script top (alongside `branch=`) or inside the fallback success block just before the DELETE. Hoisting it earlier costs one `gh` call on every cycle (including the happy auto-merge path); inlining it inside the fallback success block costs nothing on the happy path. Planner must pick — the test-shape assertions don't care about position of `gh repo view`, only about position of the DELETE relative to the fallback `gh pr merge`.
- Branch with slashes: cycle branches look like `cycle/feature/pr-sh-after-immediate-merge-fallback-suc` — `git/refs/heads/cycle/feature/...` is the correct ref path and `gh api` accepts it un-encoded. Planner should verify no URL encoding is required for `/` in ref names (it is not, per GitHub API), but should confirm before locking the regex test.
- Stderr capture pattern for the new DELETE: SPEC requires warn-and-continue on failure. Whether to capture stderr (e.g. `delete_err=$(gh api ... 2>&1 1>/dev/null) || delete_rc=$?` mirroring the existing `rc` idiom) or just suppress output (`gh api ... 2>/dev/null || true; …`) is a planner call. The existing `|| fallback_rc=$?` pattern is the closest precedent.
