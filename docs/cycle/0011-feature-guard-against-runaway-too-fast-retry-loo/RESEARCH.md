# Research: Cycle 0011

## Cycle Context
SPEC.md (`docs/cycle/0011-feature-guard-against-runaway-too-fast-retry-loo/SPEC.md`) asks for a rate-based "iteration-too-fast" guard layered on top of the existing count-based retry budget. Three coordinated changes are required: (1) a new `engine.min_step_duration_ms` config key (default `2000`, `0`/absent/malformed disables) added to the `EngineConfig` type, `src/defaults/workflows.yml`, and the synced `.cycle/workflows.yml`; (2) every `step.end` event emitted by `runCycle` must include an integer `duration_ms ≥ 0` measured around step execution; (3) the supervisor retry path in `src/cli.ts` must track consecutive sub-threshold failures of the same `(cycle_id, failing_step)`, and after `K=2` (a named constant) such failures emit exactly one `step.warning { cycle_id, step, reason: "iteration_too_fast", duration_ms, threshold_ms }` and route the cycle straight to `terminalDrain` instead of consuming the remaining `max_cycle_attempts` budget. The guard routes through the existing terminal-failure machinery — no new `engine.halted` reason — and must never crash on malformed config nor fast-bail when `duration_ms` is unreadable.

### Existing Patterns to Follow
- **Step duration / clock injection**: there is no current wall-clock measurement around steps. `runCycle` already exposes a `sleepFn` injection seam on `RunCycleOpts` (`src/engine/run-cycle.ts:232`, defaulted at `src/engine/run-cycle.ts:275`) used by rate-limit tests to make backoff deterministic. The SPEC directs extending this same `RunCycleOpts` injection seam (e.g. a clock/duration source) rather than calling `Date.now()` directly, mirroring `sleepFn`. `Date.now()` is currently used inline for rate-limit `retry_at` at `src/engine/run-cycle.ts:392` and for `retryAt` computation; the logger stamps `ts` via `new Date().toISOString()` at `src/engine/log.ts:13`.
- **`step.end` emission**: a single site emits `step.end` with `cycle_id`, `step`, `status`, `exit_code`, and a conditional `stderr` (failed only, head-capped via `truncateHeadCapped`/`MAX_STEP_END_STDERR`) — `src/engine/run-cycle.ts:489-497`. `duration_ms` would be added to this object for every step (agent and bash). `MAX_STEP_END_STDERR = 2000` is defined at `src/engine/run-cycle.ts:177`.
- **Event payload conventions**: all events go through `log.emit(event, fields)` which prepends `ts` and writes one JSON line to `.cycle/log.jsonl` plus a `console.log` sink — `src/engine/log.ts:8-18`. `step.warning` is an established event with `{ cycle_id, step, reason, ... }` shape; existing emitters at `src/engine/run-cycle.ts:328`, `:331`, `:336`, `:358-363` (reasons like `clean_failed`, `append_system_prompt_ignored`, `*_pre_sha_missing`). The SPEC's required `reason: "iteration_too_fast"` follows this exact shape.
- **Config default-with-fallback**: numeric engine keys are read as `cfg.engine.<key> ?? <default>` at use sites — e.g. `cfg.engine.rate_limit_backoff_ms ?? 3_600_000` (`src/engine/run-cycle.ts:391`), `cfg.engine.step_timeout_ms` passed through to `runStep` (`src/engine/run-cycle.ts:380`), and `cfg?.engine?.max_consecutive_failures ?? 2` (`src/cli.ts:213`). The guard's `min_step_duration_ms` default (`2000`) and disable-on-`0`/malformed semantics should be enforced at its read site, not in `loadConfig` (which performs no numeric validation today).
- **Named-constant threshold**: `SPEC_MIN_BYTES = 200` (`src/engine/run-cycle.ts:175`) and `MAX_STEP_END_STDERR = 2000` (`src/engine/run-cycle.ts:177`) are the established pattern for an exported module-level constant; `K` (default `2`) should follow this.
- **Failure handling (today)**: a step failure sets `r.status="failed"`, optionally `r.exitCode`/`r.stderr`, then `runCycle` emits `cycle.end status:"failed" failing_step` and returns `{status:"failed", failingStep}` (`src/engine/run-cycle.ts:498-509`). The child process (`run-one.ts`) exits non-zero. The supervisor reads the failing step from the log (`readCycleEndFailingStep`, `src/cli.ts:516-518`) and routes to `drainRetry` if `row.attempt + 1 < maxAttempts` else `terminalDrain` (`src/cli.ts:553-567`). `terminalDrain` increments `consecutiveFailures`, pushes to `failedCycles`, and may set `halted`/`haltReason="max_consecutive_failures"`.
- **Retry-count semantics**: `maxAttempts = max(1, wfCfg?.max_cycle_attempts ?? 3)` (`src/cli.ts:502-503`). Retry-drain leaves `consecutiveFailures` untouched (`src/cli.ts:553-555` comment); only `terminalDrain` increments it. The guard must route through `terminalDrain` so engine-level `consecutive_failures` accounting is unchanged (SPEC out-of-scope).
- **Rate-limit retry (out of scope but adjacent)**: the unbounded in-process retry loop is `src/engine/run-cycle.ts:367-399`; it is invisible to the supervisor's attempt counter (completes inside `runCycle`). SPEC explicitly excludes touching this loop.
- **Observability / log conventions**: structured JSONL at `.cycle/log.jsonl`; one event per line; `ts` auto-stamped. The supervisor reads the same file bottom-up for tail state (`readCycleEndFailingStep` `src/cli.ts:284-307`; `readLogTail`/`parseLogTail` `src/engine/log-tail.ts:21-114`). `parseLogTail` already parses `step.end` events and keys on `status`/`step` (`src/engine/log-tail.ts:48-64`) — the model for reading `duration_ms` from a `step.end`.
- **Idempotency / retry-safety**: single-engine exclusion via PID lockfile `acquireLock`/`releaseLock` on `.cycle/engine.lock` (`src/cli.ts:144-151`, `src/engine/engine-lock.ts`). Queue state persists in `tbd.jsonl`; `drainFailedRetry` preserves `cycle_id` across attempts so retries reuse the same cycle id (referenced in `docs/ENGINE.md:76`). The supervisor is a single long-running process — a module-level in-memory counter (like `consecutiveFailures` at `src/cli.ts:208`) persists across `while`-loop iterations and across an issue's retries, which is where the SPEC places the new consecutive-fast-failure counter.

## Open Questions
- **Where is `duration_ms` measured and how does the supervisor obtain it?** `runCycle` (which emits `step.end` with `duration_ms`) runs inside the spawned `run-one.ts` child; the supervisor (`cli.ts`) lives in the parent process and currently learns the failing step only by re-reading `.cycle/log.jsonl` after the child exits (`readCycleEndFailingStep`). The SPEC states the supervisor should read `duration_ms` "from the log tail" (and degrade to normal retry if the field is missing). The planner must confirm the supervisor reads the failing step's `step.end.duration_ms` from the log (analogous to `readCycleEndFailingStep`) rather than receiving it via the child exit channel.
- **Exact `step.warning` payload field naming**: SPEC requires `{ cycle_id, step, reason: "iteration_too_fast", duration_ms, threshold_ms }`. The existing config key is `min_step_duration_ms`; the warning field is `threshold_ms`. The planner should confirm the mapping (`threshold_ms` = resolved `min_step_duration_ms`).
- **Counter scope/reset wiring across resume vs main loop**: SPEC scopes the counter to the primary exec-failure retry branch only (not `runResumeOnce`). Reset triggers are enumerated (success, terminal drain, ≥-threshold failure, different failing step). The planner must decide the in-memory data structure (e.g. keyed by `cycle_id`+`step`) and where each reset fires within `src/cli.ts:467-569`.
- **`run-cycle.ts ≥ 90%` coverage with the new branch**: whether the duration-measurement and `duration_ms` emission introduce branches needing dedicated tests beyond the existing `step.end` suite (the SPEC's deterministic-clock injection is the intended mechanism).
