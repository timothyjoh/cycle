# Research: Cycle 0273

## Cycle Context
SPEC 0273 requires extending the default verify script (`src/defaults/scripts/verify.sh`) so that, in its Node/`package.json` branch, after the existing `npm test` unit run succeeds, it detects a by-convention "running-app" test suite — a `test:e2e` or `e2e` npm script, or a `playwright.config.*` / `cypress.config.*` config file — and runs it, failing verify (non-zero exit) when that suite fails. Detection must be precedence-ordered (`test:e2e` script → `e2e` script → config file via `npx`), must not match `e2e` substrings spuriously, and must degrade byte-for-byte to today's unit-only behavior in repos with no such suite (cycle's own CLI repo included). The change is confined to the default script plus `npm run sync-defaults` propagation and documentation (`docs/ENGINE.md` + `CLAUDE.md`); the engine's verify-step wiring in `run-cycle.ts` is explicitly out of scope.

## Current Codebase State

### Relevant Components
- **Default verify script (the file under change)**: `src/defaults/scripts/verify.sh:1-24`. A `set -euo pipefail` POSIX-bash script with a four-way branch: Node (`package.json` containing `"test"`) → `node_modules` guard then `npm test`; `Cargo.toml` → `cargo test`; `pyproject.toml` → `pytest` (guarded by `command -v pytest`); else a no-runner failure (`exit 1`). There is **no e2e/running-app detection anywhere** in the current script — the Node branch ends at `npm test` (`src/defaults/scripts/verify.sh:12`).
- **Synced copy (the dogfood destination)**: `.cycle/scripts/verify.sh:1-24` — currently byte-identical to the default. This is the file the running engine actually invokes for the `verify`/`final_verify` bash steps. It must be re-synced after the default changes.
- **sync-defaults pipeline**: `scripts/sync-defaults.mjs:1-135`. Copies every file under `src/defaults/` → `.cycle/`, recording a sha256 of each src/dst pair into `.cycle/.sync-state.json` (divergence guard). The recorded entry for the verify script lives at `.cycle/.sync-state.json:74` (`".cycle/scripts/verify.sh"`). Running `npm run sync-defaults` after editing the default updates both the dst file and its recorded sha; a destination diverging from both recorded shas is preserved unless `--force` (exit 2).
- **Degenerate-verification gate (sibling, already landed cycle 0272)**: `src/engine/verify-counts.ts` + the `run-cycle.ts` verify hook. Documented at `docs/ENGINE.md:283-308`. This gate parses verify stdout and fails an exit-0 run that executed zero non-skipped tests. SPEC 0273 explicitly does **not** re-implement this; it is the complementary leg ("verify must *run* the app" vs. "a skipped run can't masquerade as green"). The new docs must cross-link it (`docs/ENGINE.md:308` already names `fix-verify-must-exercise-running-app` as the sibling work).

### Existing Patterns to Follow
- **Strict-script convention**: the header comment (`src/defaults/scripts/verify.sh:1-4`) states the script is "intentionally strict. Missing dependencies are an operator problem, not a cycle problem." SPEC 0273 §Requirements aligns: a config-detected-but-runner-missing case fails loud via the `npx` non-zero exit rather than skipping silently. `set -euo pipefail` (`:5`) means any non-zero command aborts the script with that exit code — this is the mechanism by which an e2e failure propagates.
- **Branch-selection idioms**: existing detection uses `[ -f package.json ]`, `grep -q '"test"' package.json`, `[ -d node_modules ]`, and `command -v pytest &>/dev/null` (`src/defaults/scripts/verify.sh:7-19`). New e2e detection should follow the same `[ -f ... ]` / glob / npm-script-presence idioms. To match a script key precisely (avoid spurious `e2e` substring matches per SPEC §Requirements), the existing `grep -q '"test"'` is a loose precedent; a tighter key-anchored check (e.g. `npm pkg get scripts.test:e2e`, or a quoted-key grep like `"test:e2e"`) is what the SPEC's "match the script key by convention, not loose substring" calls for — the planner resolves the exact mechanism.
- **Failure handling (today)**: there is no retry/fallback inside the script — it fails closed via `pipefail` and explicit `exit 1` guards. Guards print an actionable message to **stderr (fd 2)** and exit 1 (`src/defaults/scripts/verify.sh:9,17,22`). A test runner's failure cause goes to **stdout**, which the engine captures separately (see Observability).
- **Observability (engine-side, unchanged by this cycle)**: a failed `bash` step gets a head-capped `stdout` excerpt on `step.end` plus a full `<artifactDir>/<step>.out` artifact (`stdout_artifact` pointer), per `docs/ENGINE.md:276` and CLAUDE.md (*Failed bash-step stdout capture*). So an e2e failure surfaced on stdout is captured by the existing failed-bash path; the script needs only to exit non-zero. The verify step's degenerate-gate events (`verify.unverified`) are emitted by `run-cycle.ts`, not the script.
- **Idempotency / retry-safety**: the script itself is stateless and side-effect-free aside from invoking test runners; re-running it is safe. Cycle-level retry/teardown (`max_cycle_attempts`, `cycle.restart`) is engine-side and untouched here.

### Test Infrastructure
- **Test framework**: `node:test` + `node:assert/strict`, driven via `npm test` (auto-builds first). No transpile step.
- **Closest existing test module**: `tests/defaults/scripts.test.ts:1-133` — the canonical pattern for this cycle. It resolves an absolute `bash` path (`resolveBash()`, `:16-24`), defines `runVerify(seed, env)` which seeds a `mkdtempSync` tmpdir, writes a fixture `package.json`/`pyproject.toml`, then `spawnSync(BASH, [VERIFY_SH], { cwd: dir, env, timeout: 30000 })` (array args, `shell:false` — per subprocess discipline) and removes the tmpdir in `finally` (`:28-36`, `:100-132`). `assertGuardFired` (`:40-51`) asserts `status === 1` and the actionable message is on **stderr not stdout**. Two curated PATH envs exist: `HERMETIC_ENV = { PATH: "" }` (`:57`) and `NODE_GUARD_ENV = { PATH: process.env.PATH }` (`:63`). Several tests assert on the script *body text* via `readFile` + regex (`:75-98`).
- **Test conventions**: temp-dir fixtures with fake npm scripts (e.g. `scripts.test` currently); SPEC §Testing Strategy prescribes fast fake scripts (`"test:e2e": "exit 0"` / `"exit 1"`) and a sentinel file written by a fake e2e script to assert the e2e command actually ran. The SPEC suggests a new module `tests/scripts/verify-sh.test.ts`, though the existing equivalent module already lives at `tests/defaults/scripts.test.ts` (the planner chooses placement).
- **Current coverage of the change area**: `tests/defaults/scripts.test.ts` covers the node_modules-absent guard, pytest guard, no-runner guard, shebang/executable, and "does not invoke npm install" (`:65-132`). There is **no existing test that runs `npm test` to success** (all current spawn tests hit a guard that exits before `npm test`), so the happy-path/e2e-passing scenario is new ground; fixtures will need a `node_modules/` directory (or a fake `npm` on PATH) so the Node branch proceeds past the `node_modules` guard to actually run the unit then e2e commands.
- **Failure-path test coverage (today)**: failure paths *are* covered for the existing guards (node_modules absent, pytest absent, no runner) at `:100-132`. SPEC §Acceptance adds new failure-path fixtures: e2e-present-and-failing, and config-only-runner-fails. The `scripts/coverage-gate.mjs` floors do not list `verify.sh` (it is a shell script, not LCOV-tracked), so coverage is enforced via the spawn tests' behavioral assertions rather than a numeric floor.

## Open Questions
- **Config-only invocation form**: SPEC §Requirements says "invoke the corresponding runner via `npx`" when only a config file is present and no script exists. The exact command per framework (`npx playwright test` vs `npx cypress run`) and how to select between a detected `playwright.config.*` and `cypress.config.*` is for the planner to specify.
- **Precise script-key matching idiom**: the SPEC forbids loose `e2e` substring matches; whether to use `npm pkg get`, a quoted-key grep, or another mechanism to detect `test:e2e`/`e2e` script keys is unresolved here.
- **Happy-path fixture for the unit run**: existing tests never reach a successful `npm test`. Whether the new passing-path fixtures stub `npm` on a curated PATH or seed a real `node_modules/` + minimal package is a planning decision (the SPEC's fake-script approach implies stubbing the commands the script invokes).
- **Doc placement**: whether the new verify-policy prose extends the existing *Degenerate verification gate* section in `docs/ENGINE.md` or gets its own subsection — the SPEC permits either ("or the verify-policy doc").
