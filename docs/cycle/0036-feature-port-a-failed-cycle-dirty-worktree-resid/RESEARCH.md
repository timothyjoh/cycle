# Research: Cycle 0036

## Cycle Context
SPEC 0036 requires porting the **failed-cycle dirty-worktree residue guard** from the divergent `recon` cycle lineage into mainline. After a cycle ends in terminal failure, and **before** either (a) the resume/retry path or (b) the next-pending-issue loop path acts on the next unit of work, the engine must check the worktree for uncommitted residue (excluding engine-owned runtime state). If residue is present it halts cleanly with `engine.halted { reason: "failed_cycle_dirty_worktree", failed_cycle_id, issue_id, dirty_paths, message }` (cardinality-pinned, exactly-once), the existing terminal `engine.stop`, and a `formatFailedCycleResidueDiagnostic`-style message written to `process.stderr`; a clean tree proceeds byte-for-byte unchanged. Scope: a new pure module `src/engine/failed-residue-guard.ts` (a `git status --porcelain --untracked-files=all` snapshot reader + diagnostic formatter), wiring into the `src/cli.ts` supervisor on both gated paths, tests, docs, a per-file coverage floor, and possibly a structural-invariant entry. Cross-process persistence (recon's `.cycle/failed-residue-context.json` startup re-check), auto-remediation, and the `claude -p` exit-hang root cause are explicitly out of scope.

Confirmed: mainline (`src/`) has **zero** existing hits for `failed_cycle_dirty_worktree`, `formatFailedCycleResidueDiagnostic`, `residue`, or `failed-residue` — this cycle introduces all of them. This is not a no-op.

## Open Questions
- **Engine-owned exclusion source of truth**: `isDenied` (`path-utils.ts:4-12`) does not currently exclude `.cycle/log.jsonl`, `.cycle/tbd.jsonl`, `.cycle/run.log`, or `.cycle/queue` state — only `*.lock`, `.cycle/cycle.pid`, and the `.claude`/`dist`/`node_modules` prefixes. The planner must decide whether to extend `isDenied` (which is also used by commit-cycle/run-cycle touched-file accounting — changing it has blast radius) or maintain a guard-local exclusion list of engine-owned runtime paths. SPEC says "reuse `isDenied`/`path-utils` scoping where it fits rather than re-hand-coding a parallel list."
- **Snapshot reader semantics**: mainline's `parseSnapshotPaths` (`run-cycle.ts:91`) filters untracked files to `src/`/`scripts/` prefixes only; the recon residue reader keeps all untracked paths. The new `failed-residue-guard.ts` needs the unfiltered behavior — the planner must decide whether to add a new parse function in the guard module or generalize the existing one (the latter would change empty-diff/touched-file behavior and is risky).
- **Resume-path accounting divergence**: the resume call-site (`src/cli.ts:514-521`) inlines terminal accounting and does **not** call `recordTerminalFailure`, while the loop path does. The planner must capture the residue context on **both** terminal paths; recon's `pendingFailedResidueContext` model (set on terminal failure, checked at the top of the next iteration / before next resume) is the reference, but mainline's single-process in-loop structure differs.
- **Where exactly the guard runs**: recon checks at startup (persisted context, out of scope here) and at the top of the loop / before resume using an in-memory `pendingFailedResidueContext`. For mainline's in-scope single-process variant, the planner must place the check so it gates the resume call (`src/cli.ts:508`) and the next-issue `popNextPending` (`src/cli.ts:542`) without firing on a clean post-success state — i.e. only when a terminal failure was just recorded.
- **`engine.stop` payload fields on the new halt**: recon's residue `engine.stop` includes `reason: "failed_cycle_dirty_worktree"`, `halted_at_issue`, `failing_step` (recon `cycle.js:10706-10713`), and sets an `engineStopEmitted` flag to avoid a double `engine.stop` from the existing epilogue (recon `cycle.js:10714`). Mainline's epilogue at `src/cli.ts:721-729` always emits one `engine.stop`; the planner must ensure exactly one terminal `engine.stop` fires on the residue-halt path (suppress or route through the epilogue).
- **Structural invariant**: whether to add an `INVARIANTS` entry pinning the two guard call-sites (mirroring recon's ordering assertions) or rely on the supervisor behavioral tests — SPEC leaves this conditional ("if warranted").
