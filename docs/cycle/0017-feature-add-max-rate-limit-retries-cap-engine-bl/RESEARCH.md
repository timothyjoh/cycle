# Research: Cycle 0017

## Cycle Context
This cycle bounds the rate-limit retry loop in `runCycle` (`src/engine/run-cycle.ts`), which today is a `while (true)` that exits only on clean success or a non-rate-limit failure. SPEC.md requires adding an optional `max_rate_limit_retries?: number` field to `EngineConfig` (`src/engine/workflow.ts`) and to the `engine:` block of `src/defaults/workflows.yml` (default `24`), then tracking a per-step consecutive-rate-limit counter inside the retry loop. When the counter exceeds the cap, the loop must stop *before* the next sleep/retry, emit `engine.halted { reason: "rate_limit_max_retries", retries: N, step_index: i }`, and return `{ cycleId, artifactDir, status: "failed", failingStep: step.name }` so the caller routes it through the unchanged terminal-failure path. A `0`/negative/non-integer/malformed configured cap must degrade defensively at the read site to the default `24`. Documentation (`CLAUDE.md`, `docs/ENGINE.md`) and boundary tests in `tests/engine/rate-limit-integration.test.ts` are part of the deliverable.

### Existing Patterns to Follow
- Read-site defensive coercion for malformed numeric config (the pattern SPEC.md mandates): the iteration-too-fast guard resolves `min_step_duration_ms` at its read site — `src/cli.ts:529`–`535`: `const rawMin = cfg?.engine?.min_step_duration_ms; const thresholdMs = typeof rawMin === "number" && Number.isFinite(rawMin) && rawMin > 0 ? rawMin : 0;` with an explanatory comment. `compress_output` is similarly resolved as `=== true` at `src/engine/run-cycle.ts:376`. Note: `loadConfig` does **not** validate or coerce these numeric engine fields — they pass through verbatim from YAML (`src/engine/workflow.ts:74`, returned as `parsed as CycleConfig` at `:140`), so all defaulting/validation happens at read sites.
- Structured-event observability: all engine events go through `await log.emit("<event>", { ... })` where `log = await createLogger(repoRoot)` (`src/engine/run-cycle.ts:240`), appending one JSON line to `.cycle/log.jsonl`. Existing rate-limit events: `engine.paused { reason, retry_at }` (`:421`) and `engine.resumed { reason }` (`:429`).
- `engine.halted` emission convention: today emitted **only** at the supervisor level in `src/cli.ts:646`–`651` as `engine.halted { failed_cycles, reason: "max_consecutive_failures", threshold }`. This cycle introduces a **new** emission site inside `runCycle` with `reason: "rate_limit_max_retries"`. `engine.halted` is a canonical exactly-once event (per CLAUDE.md test conventions).
- Failed-cycle return shape: `return { cycleId, artifactDir, status: "failed" as const, failingStep: step.name }` — `src/engine/run-cycle.ts:564` (the existing terminal-failure return, preceded by `await log.emit("cycle.end", { cycle_id: cycleId, status: "failed", failing_step: step.name })` at `:563`). The success return is `{ cycleId, artifactDir, status: "ok" as const }` at `:569`.
- Failure handling today: the rate-limit loop is currently unbounded by design — it retries forever, throttled only by the 1-hour backoff (`src/engine/run-cycle.ts:419`; documented as a known limitation in `docs/ENGINE.md:322` and `:339`). Non-rate-limit failures `break` the loop and fall through to the post-step failure routing at `src/engine/run-cycle.ts:554`–`565` (reflection/documentation steps `continue`; all others emit `cycle.end` failed and return).
- `finally`-block cleanup contract: the `try` body's early `return` still runs the `finally` block (`src/engine/run-cycle.ts:570`–`597`), which performs checkout (`cycle.checkout`) and base-pull (`cycle.base_pull`) bookkeeping. SPEC.md requires the new early `return` to preserve this — it does, since it returns from inside the same `try`.
- Idempotency / retry-safety: the new counter must be **per-`runCycle`-invocation, per-step, non-persistent** (SPEC.md Out of Scope). The existing loop uses a local `wasRateLimited` boolean (`src/engine/run-cycle.ts:393`) scoped to a single step iteration of the `for (let i = startIdx; ...)` loop (`:285`); a `rateLimitRetries` counter should be declared at the same scope (reset per step). Rate-limit retries complete inside `runCycle` and are invisible to `run-one.ts`, so they do not increment the supervisor's `consecutive_failures`.

## Open Questions
- Counter scope/semantics: SPEC.md says the counter is per-step within a single `runCycle` call. The planner must confirm where to declare/reset the counter relative to the existing per-step `wasRateLimited` (`src/engine/run-cycle.ts:393`) so that resuming to a different step index (`opts.resume.startStepIndex`) starts from zero. (SPEC.md states the counter is per-`runCycle`-invocation, per-step, non-persistent — the resolution is to declare it inside the per-step iteration alongside `wasRateLimited`.)
- Off-by-one boundary: SPEC.md acceptance requires "rate-limit exactly `cap` times then succeed → no halt" and "`cap + 1` times → halt" with `engine.halted.retries` carrying the actual observed count. The planner must pin the exact comparison (increment-then-compare vs compare-then-increment) so that the `retries` value and the `cap`/`cap+1` boundary match the acceptance tests; SPEC.md phrases it as "the first attempt that pushes the count past the cap" / "the counter exceeds the configured cap."
- `engine.halted` field set: SPEC.md specifies `{ reason, retries, step_index }` for the in-`runCycle` emission, whereas the supervisor's existing `engine.halted` carries `{ failed_cycles, reason, threshold }` (`src/cli.ts:647`). The planner should confirm no consumer asserts a single uniform `engine.halted` schema across both emission sites.
