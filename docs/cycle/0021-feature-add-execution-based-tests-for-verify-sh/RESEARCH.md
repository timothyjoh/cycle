# Research: Cycle 0021

## Cycle Context
This cycle adds hermetic, execution-based tests to `tests/defaults/scripts.test.ts` that actually run `bash src/defaults/scripts/verify.sh` from controlled tmpdir fixtures and assert observable exit code and stderr for the three real fail-fast guard branches in `verify.sh`: (a) a Node project (`package.json` with a `"test"` script) missing `node_modules/`; (b) a Python project (`pyproject.toml`) with `pytest` absent from PATH; (c) no recognized test runner present. ### Existing Patterns to Follow
- **`spawnSync` with array args, controlled `cwd`/`env`** is the established subprocess-from-test pattern — `tests/cli/help.test.ts:6,46,86-90`. Example: `spawnSync("node", [dist], { cwd: root, encoding: "utf8", timeout: 30000 })`. Use `spawnSync("bash", [absVerifyPath], { cwd, env, encoding: "utf8" })`. Subprocess discipline (CLAUDE.md): always `spawn`/`spawnSync` with array args, never `exec`/`execSync`, never `shell: true`.
- **tmpdir fixtures + cleanup**: `mkdtemp(join(tmpdir(), "cycle-…-"))` then `try { … } finally { await rm(root, { recursive: true, force: true }); }` — `tests/cli/help.test.ts:83-101`. Imports `tmpdir` from `node:os`, `join` from `node:path`. The SPEC requests synchronous `fs.mkdtempSync` / `rmSync` and per-test or `t.after` teardown (`node:test` exposes a `t.after` hook; `try/finally` with the async `node:fs/promises` helpers is the dominant existing convention in `help.test.ts`).
- **Status / stderr assertions on spawnSync results**: assert `r.status` and surface `r.stderr` in the failure message — `tests/cli/help.test.ts:47` (`assert.equal(r.status, 0, \`expected exit 0, got ${r.status}. stderr: ${r.stderr}\`)`). For the new tests: read `result.status` and `result.stderr.toString()` directly; the SPEC requires a `null`/non-`1` status to fail the test rather than pass silently, and a `result.error`-set launch failure to fail loudly.
- **Test framework imports**: `import { test } from "node:test"` and `import { strict as assert } from "node:assert"` — `tests/defaults/scripts.test.ts:1-2`, also `tests/cli/help.test.ts:1-2`. The existing file already imports from `node:fs/promises` (`readFile`, `stat`) — `tests/defaults/scripts.test.ts:3`.
- **`encoding: "utf8"`** on `spawnSync` makes `stdout`/`stderr` strings; `help.test.ts` uses this (`r.stdout.includes(...)`). The SPEC phrases assertions as `result.stderr.toString()`, which works whether the result is a string or Buffer.
- **Writing minimal bash-script fixtures in tests**: `await writeFile(scriptPath, "#!/bin/bash\nexit 0\n", "utf8")` — `tests/cli/engine-lock-integration.test.ts:45`; inline verify.sh fixtures appear at `tests/cli/halt.test.ts:209`. Demonstrates the fixture-write idiom for branch selection (here: write `package.json` / `pyproject.toml` / nothing).
- **Failure handling (existing approach in the change area)**: `verify.sh` is fail-fast — `set -euo pipefail` (`src/defaults/scripts/verify.sh:5`) plus explicit `exit 1` in each guard. The script writes operator-actionable messages to stderr (`>&2`) and never to stdout for the guard paths. Tests currently assert this only by reading the script text; there is no existing execution-based failure-path test for these branches. The repo convention (CLAUDE.md → Test conventions) emphasizes cardinality-pinned assertions for exactly-once *engine events*, which is not directly applicable here (no engine events involved), but the "assert observable behavior, fail loudly" spirit applies.
- **Observability**: not applicable to `verify.sh` itself — it emits to stderr/stdout only; there is no `.cycle/log.jsonl` event surface in this script. The cycle's observability target is the test's own assertions on `status`/`stderr`/`stdout`.
- **Idempotency / retry-safety**: tests must be hermetic and deterministic per SPEC — branch selection driven purely by tmpdir fixture contents plus a curated `env.PATH` (excluding `pytest`/`npm` where required), so repeated runs are identical regardless of host tooling. No locks/dedup keys involved; the isolation mechanism is the per-test `mkdtempSync` directory + teardown.

## Open Questions
- **Teardown style**: SPEC mentions both `t.after` and per-test cleanup; the existing file (`tests/defaults/scripts.test.ts`) uses no temp dirs yet, while the closest pattern (`tests/cli/help.test.ts:100-101`) uses `try/finally` with async `rm`. Planner should pick one consistent with `spawnSync`/`mkdtempSync` synchronous fixtures (SPEC suggests sync `fs` APIs) — either is acceptable; this is a style choice, not a behavioral constraint.
- **PATH minimization for the Python guard**: SPEC requires a PATH lacking `pytest`. Planner must confirm that an empty or minimal `env.PATH` still lets `bash` start and run builtins (`command -v`, `echo`, `[`) — these are bash builtins so an empty PATH is expected to suffice, but the planner should verify the spawned `env` does not need to inherit anything beyond what `spawnSync("bash", …)` requires to launch the interpreter found at its absolute/resolved path. (`spawnSync("bash", …)` itself resolves `bash` via the parent process PATH unless an absolute bash path is used.)
- **Node guard without triggering `grep`/`npm`**: the Node branch requires `package.json` containing `"test"`; the guard fires before `npm test` runs because `node_modules` is absent, so no `npm` binary is invoked. Planner should ensure the fixture `package.json` contains a `"test"` key so `grep -q '"test"'` matches and the branch is selected.
