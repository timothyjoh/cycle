# Research: Cycle 0267

## Cycle Context
SPEC 0267 asks for a single new **relational/predicate (`validate`-style)** entry in the `INVARIANTS` table of `scripts/structural-invariants.mjs` that enforces the safety-critical convention established by cycle 0265: every in-process step lane under `src/engine/exec-*.ts` that calls `spawn(` must also call **both** `registerActiveChild` and `unregisterActiveChild` (so `run-one`'s suspend handler can reap the detached child subtree). A lane with no `spawn(` call passes vacuously. The check must run only through the existing `runInvariants` dispatch (import-safe, no top-level side effects), return `{ ok, actual?, message? }` (a structured `{ ok: false, message }` naming the file and missing call for the genuine missing-call case rather than throwing), and be covered by in-process tests in `tests/scripts/structural-invariants.test.ts` exercising pass / fail / vacuous branches plus the dispatch-level integration. No exec-lane runtime behavior changes; one CLAUDE.md note is updated. This is **not** a no-op — the invariant does not exist yet (verified: no `registerActiveChild`/`active-child` reference in `scripts/structural-invariants.mjs`).

### Existing Patterns to Follow
- **Relational invariant shape**: `{ file, validate, reason }` where `validate(text, file) => { ok: boolean, actual?: string, message? }`. The predicate splits `text` into lines, scans with module-level `RegExp` constants, accumulates violations, and returns `{ ok: false, message }` (naming offending lines) or `{ ok: true, actual: "<n> paired" }`. Model: `validateResidueArmPersist`, `scripts/structural-invariants.mjs:48-76`. Module-level regex constants are declared near the top (`scripts/structural-invariants.mjs:24-28`).
- **Per-file granularity constraint**: `runInvariants` reads exactly one file per entry (`scripts/structural-invariants.mjs:256-267`). A predicate's `text` argument is the contents of that single `entry.file`. To cover the whole `exec-*.ts` set with the existing dispatch unchanged, the natural pattern is **one relational entry per `exec-*.ts` file** (each invoking the same shared named predicate), so a non-spawning lane returns `{ ok: true }` vacuously and a spawning lane is checked. The SPEC frames this as "one new entry" / a single predicate; the planner must reconcile this with the one-file-per-entry dispatch (e.g. one shared predicate function reused across per-file entries, or a single entry pointed at the canonical spawning lane(s)). The `reason` string is reused across grouped count entries already (e.g. the hermeticity block, `scripts/structural-invariants.mjs:133-241`).
- **Import-safety**: the gate (file-read loop + `process.exit`) runs only under the `import.meta.url === pathToFileURL(process.argv[1]).href` main guard (`scripts/structural-invariants.mjs:310-318`). `INVARIANTS` and `runInvariants` are plain exports importable without side effects. Any new predicate must be a pure top-level function with no side effects at module load.
- **Type-checking the `.mjs`**: the file carries `// @ts-check` (`scripts/structural-invariants.mjs:2`) and the `Invariant` typedef (`:30-42`) with JSDoc; repo-wide `allowJs` type-checks it. The `validate` field is typed `(text: string, file: string) => { ok: boolean, actual?: string, message?: string }` (`:41`). A new predicate must match this signature to keep `npm run typecheck` clean.
- **Failure handling**: a thrown predicate is contained as a FAIL by the dispatch `try/catch` at `scripts/structural-invariants.mjs:273-280` (emits `predicate threw: <msg>`, `failed++`, continue) — never coerced to a silent pass. A falsy / `!ok` result emits `structural-invariants: FAIL <file> -- <reason>: <message>` (`:281-285`). An unreadable target file throws a tagged `exitCode = 2` error (`:261-267`) surfaced by the CLI guard. The SPEC requires the new predicate itself to **return** `{ ok: false, message }` for the missing-call case (not throw), so the operator sees the actionable name.
- **Observability**: the gate writes human diagnostics to `console.error` (FAIL) and `console.log` (ok) — `scripts/structural-invariants.mjs:282-297`. There is no `.cycle/log.jsonl` structured event for the gate; the FAIL/ok stdout/stderr lines are the convention. Pass line format: `structural-invariants: ok -- <file> <reason>: <actual>`.
- **Idempotency / retry-safety**: the gate is a pure read-only check (no locks, no state mutation); re-running is deterministic against the tree. No guard machinery to respect beyond the dispatch contract.

## Open Questions
- **Entry granularity vs. "one entry"**: the dispatch reads one file per entry, but the SPEC asks for "a single new relational entry" covering "every `src/engine/exec-*.ts` lane." The planner must decide whether to (a) register one shared named predicate across one entry per `exec-*.ts` file (vacuous-pass on non-spawners — matches the "lane with no `spawn(` passes vacuously" requirement most directly), or (b) target only the canonical spawning lane(s). The current dispatch does not glob a file set within a single entry.
- **`setup` helper impact**: the subprocess `run(cwd)` tests rely on `setup` writing `src/engine/exec-<agent>.ts` stubs (`tests/scripts/structural-invariants.test.ts:39-45`); if the new invariant adds per-`exec-*.ts` entries, `setup`'s stub lanes (and/or the missing `exec-spawn.ts` / `exec-bash.ts` stubs, which `setup` does not currently write) may need to satisfy the new invariant so the existing clean-fixture subprocess tests (`:71-82`, `:101-113`, etc.) still exit 0. The planner should confirm which files `setup` must add to keep those tests green.
- **`detached: true` enforcement**: explicitly out of scope per SPEC (`:27`); the minimal check is the register/unregister pairing only.
