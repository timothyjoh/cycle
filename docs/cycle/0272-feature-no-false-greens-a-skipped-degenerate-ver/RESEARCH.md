# Research: Cycle 0272

## Cycle Context
SPEC.md asks the engine to recognize a **degenerate verification** — a `verify` (or `final_verify`) bash step that exits 0 but executed **zero** non-skipped tests — and route it through the existing step-failure path as *unverified* instead of draining the issue to `done/ ok`. The work has three parts: (1) a new pure parser `src/engine/verify-counts.ts` extracting `{ executed, skipped, total }` from common reporter summaries (vitest/jest, node:test, pytest, cargo), returning `null` when no recognized summary is found; (2) a run-cycle hook that, after a bash step named `verify`/`final_verify` exits 0, parses its captured stdout and — when `executed === 0` and (`skipped > 0` or `total > 0`) — sets `r.status = "failed"`, emits `verify.unverified { cycle_id, step, executed, skipped, total, reason }`, and surfaces a `verification incomplete: N tests skipped, 0 executed — cannot confirm the app works` diagnostic via stderr; (3) a defensively-coerced `engine.verify_min_executed` knob (default `1`). The gate is **fail-closed** on a confident degenerate parse and **fail-open** (byte-for-byte unchanged) when output is unparseable.

## Current Codebase State

### Relevant Components
- **Step dispatch + per-step result handling**: the `while (true)` step loop in `runCycle` dispatches bash steps via `execBashStep` and agent steps via `resolveAgent(...).runStep` — `src/engine/run-cycle.ts:646-715`. The bash branch is `src/engine/run-cycle.ts:647-649`; the full `StepResult` (with un-truncated `r.stdout`) is in scope from there through `step.end`.
- **`StepResult` shape** (what the parser will read): `{ status, exitCode, stdout, stderr, rateLimited?, timedOut? }` — `src/engine/exec-types.ts:1-9`. `r.stdout` holds the **complete** captured stdout buffer in memory (accumulated in `execBashStep` via `child.stdout.on("data", …)` — `src/engine/exec-bash.ts:42`); head-capping happens only when writing the `step.end` event field, not to the buffer itself.
- **Bash-step success path**: a successful bash step currently has **no special post-success handling** — the `if (step.agent !== "bash")` block at `src/engine/run-cycle.ts:722-891` is skipped entirely for bash steps, so control falls from the step loop straight to the failed-bash capture (`src/engine/run-cycle.ts:898-914`, gated on `r.status === "failed"`) and then `step.end` (`src/engine/run-cycle.ts:915-928`). The new verify hook must sit between the loop exit (`src/engine/run-cycle.ts:715`) and `step.end`, in the bash path.
- **Verify steps are bash steps named `verify` / `final_verify`** running `scripts/verify.sh`: declared in every workflow — `src/defaults/workflows.yml:37,40` (feature: `verify` + `final_verify`), `:51` (document), `:61` (quickfix), `:73` (e2e-tests). Synced copy: `.cycle/workflows.yml` (same line numbers). The default `verify.sh` runs `npm test` / `cargo test` / `pytest` — `src/defaults/scripts/verify.sh`.
- **Config type `EngineConfig`**: `src/engine/workflow.ts:35-73`. New knob `verify_min_executed?: number` is added here.
- **`loadConfig`**: `src/engine/workflow.ts:110-192`. Note that read-site-coerced knobs (`compress_output`, `max_rate_limit_retries`) are **not** coerced in `loadConfig` — only `commit`, `shell`, and per-step `timeout_ms` are normalized there. `verify_min_executed` follows the read-site-coercion convention.

### Existing Patterns to Follow
- **Pure classifier module + fail-closed reader** (direct model for `verify-counts.ts`): `src/engine/noop-marker.ts` — exports a `Set` of recognized tokens (`NOOP_REASONS`, `:6-10`), a discriminated return type (`NoopClassification`, `:12-14`), a pure `parseNoopMarker(content): NoopClassification` that **never throws** (`:25-38`), and an async fail-closed file reader `classifyNoopMarker` (`:43-51`). The SPEC's parser is the pure half: a string-in / `{ executed, skipped, total } | null`-out function with no I/O.
- **Regex-table parsing style**: `noop-marker.ts:20-21` declares module-level `RegExp` constants and matches line-by-line. The verify parser must recognize vitest/jest (`Tests: N passed, M skipped`), node:test (`# tests` / `# pass` / `# skip`), pytest (`N passed, M skipped`), cargo (`test result: ... N passed; M ignored`).
- **Read-site defensive coercion of an integer engine knob** (direct model for `verify_min_executed`): `max_rate_limit_retries` — `src/engine/run-cycle.ts:643-645`: `const rawCap = cfg.engine.max_rate_limit_retries; const maxRateLimitRetries = typeof rawCap === "number" && Number.isInteger(rawCap) && rawCap > 0 ? rawCap : 24;`. The same `typeof === "number" && Number.isInteger && >= 0` guard, defaulting to `1`, is the SPEC's prescribed pattern. Compare also `coerceTimeout` (`src/engine/workflow.ts:94-95`) and the `compress_output === true` read (`src/engine/run-cycle.ts:612`).
- **Setting `r.status = "failed"` to route a green step through the failure path** (the exact mechanism the hook reuses): the completion-proof check at `src/engine/run-cycle.ts:760-763` (`r.status = "failed"; r.exitCode = r.exitCode || 1; r.stderr = proofError;`) and the empty-diff guard at `src/engine/run-cycle.ts:843-845`. Both turn an exit-0 step into a retryable failure with a formatted stderr message; the verify hook does the same.
- **Formatted-error helper convention**: `formatEmptyDiffGuardError` / `formatCompletionProofError` / `formatTimeoutProofError` are exported pure string builders — `src/engine/run-cycle.ts:311-321`. A `verification incomplete: …` formatter should follow this (exported, pure).
- **Structured-event emission**: `await log.emit("<event>", { cycle_id: cycleId, step: step.name, … })` — e.g. `step.completion_check` (`src/engine/run-cycle.ts:754-759`), `step.output_capture_failed` (`:907-912`), `cycle.noop` (`:933-938`). The new event is `verify.unverified { cycle_id, step, executed, skipped, total, reason }`.
- **Failure handling today**: a `verify` bash step that exits non-zero already yields `r.status = "failed"` from `execBashStep` (`src/engine/exec-bash.ts:50-57`); the failed-bash capture writes a `<step>.out` artifact and head-capped `stdout`/`stderr` excerpts to `step.end` (`src/engine/run-cycle.ts:898-928`), and the cycle routes through the `max_cycle_attempts` retry / terminal-drain machinery in `src/cli.ts`. The hook must **not** alter the non-zero-exit path — it fires only when the step already exited 0.
- **Observability conventions**: append-only JSONL via `log.emit` to `.cycle/log.jsonl`; **exactly-once** engine events are cardinality-pinned with `filter(predicate).length === 1` (CLAUDE.md *Test conventions*; canonical examples `engine.halted`, `reflection.summary`). `verify.unverified` must fire exactly once per degenerate step and be tested that way.
- **Idempotency / retry-safety**: the per-step loop re-runs from `startStepIndex` on resume; the hook is stateless and re-derives its decision from `r.stdout` each run, so it is retry-safe. No locks or dedup keys are involved at the step level (engine-level locking lives in `src/engine/engine-lock.ts`, out of scope here).
- **Fail-closed/fail-open split precedent**: the build-phase empty-diff guard is marker-gated and preserves `formatEmptyDiffGuardError` byte-for-byte when no valid marker exists (`src/engine/run-cycle.ts:824-847`); the no-op research short-circuit is fail-closed via `classifyNoopMarker` (`:861-872`). The verify gate mirrors this: confident degenerate parse ⇒ block; `null` ⇒ no event, no status change.

### Dependencies & Integration Points
- **`r.stdout`** (full buffer) — the parser's input; already in scope at the hook site. No new capture machinery is required to *see* the summary (reporter summaries appear at the tail of stdout, and `r.stdout` is the complete buffer). The SPEC's note about tail-capping concerns only what is *persisted to the event field* (`MAX_STEP_END_STDOUT = 2000`, head-capped via `truncateHeadCapped` — `src/engine/run-cycle.ts:302`, `src/engine/log-fmt.ts:1-3`), not the in-memory buffer the parser reads.
- **`cfg.engine.verify_min_executed`** — read inside `runCycle` from the loaded `CycleConfig` (`loadConfig`, `src/engine/run-cycle.ts:2` import).
- **`log.emit`** (`Logger`, `src/engine/log.ts`) — the event sink.
- **Step-failure / retry machinery** — `src/cli.ts` supervisor + `max_cycle_attempts` (no new halt reason introduced; the hook reuses `r.status = "failed"`).
- **`step.name` keying** — the hook gates on `step.name === "verify" || step.name === "final_verify"` and `step.agent === "bash"` and `r.status === "ok"` (mirrors the name-keyed gates at `src/engine/run-cycle.ts:772`, `:850` and the walkthrough phase map at `:49-53`).

## Open Questions
- **Reporter summary regexes — exact tail formats.** The SPEC names four reporters; the planner should pin the canonical summary lines (e.g. vitest `Tests  N passed | M skipped (T)` vs jest `Tests:       N passed, M skipped, T total`; node:test `# tests N` / `# pass N` / `# skip N` / `# todo N`; pytest `===== N passed, M skipped in …s =====`; cargo `test result: ok. N passed; 0 failed; M ignored; …`). The precise mapping of `executed` (= non-skipped that actually ran) and `total` per reporter (e.g. node:test `executed = pass + fail`; whether `todo` counts toward `skipped`) is a parser-design decision left to plan.
- **`engine.verify_min_executed` semantics vs the SPEC's `executed === 0` rule.** The SPEC's hook description blocks on `executed === 0`, while the knob default is `1`. The planner should confirm whether the gate condition is literally `executed < verify_min_executed` (with the `null`/no-skips-and-no-total escape) or strictly `executed === 0` with the knob only setting the floor — and how the `(skipped > 0 || total > 0)` precondition interacts with the threshold.
- **`final_verify`-then-block interaction with later steps.** In the feature workflow `final_verify` (`src/defaults/workflows.yml:40`) is followed by `documentation` and `walkthrough_capture`. The planner should confirm that flipping `final_verify` to `failed` routes through the same terminal/retry path as a non-zero `final_verify` exit does today (it should, since both set `r.status = "failed"` before `step.end`), with no special-casing needed.
- **Whether the degenerate verify output should also be persisted to a `.out` artifact.** On a degenerate verdict `r.status` becomes `"failed"`, which would trigger the existing failed-bash `.out` capture (`src/engine/run-cycle.ts:898-914`) — confirm this is the intended surfacing and that no separate artifact is required.
